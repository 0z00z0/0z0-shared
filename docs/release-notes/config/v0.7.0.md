**Two new assemblies join the config component, and the plain settings file stops overwriting a file
it could not read.** `ZeroZero.Config.Sections` is one settings document whose top-level keys belong
to different components, addressed a section at a time. `ZeroZero.Config.Watch` picks up an edit made
outside the application. `ZeroZero.Config` itself gains a write latch and a flush to disk.

**Minor rather than patch.** No public member is removed and nothing needs recompiling, but a write
that used to succeed can now legitimately fail, and a consumer that ignores the result of a save will
not notice.

## The write latch — the one behaviour that changed

**A settings file that is present but cannot be read no longer gets overwritten with defaults.**

A file held open by another process, or one the process is denied, used to read as defaults; the next
`Update` or `Save` then wrote those defaults over it, and the user's settings were gone. The store
now refuses to write until one read has succeeded, returning an `InvalidOperationException` in the
save result and raising `SaveFailed`.

The latch is set once and never cleared, so writing a good configuration over a file someone broke by
hand still works. A `Reload` that meets the same failure keeps what is held rather than falling back
to defaults.

**One path deliberately bypasses the latch**: a file that parses as nothing at all is quarantined and
replaced at construction, because there is nothing to preserve. The quarantined copy is the only
surviving record and nothing puts it on screen, so a host that never reads `LastQuarantinePath`
leaves its user with no settings and no explanation.

## The write reaches the disk before the rename

The atomic write already went to a temporary sibling and retried a replace the system refused for a
moment, but the bytes could still be in the operating system's cache when the rename landed — so a
power loss could leave the new name pointing at nothing. It now flushes to disk first.

The write also moved out of `SettingsFile<T>` into a public **`AtomicFile`**, so a caller writing raw
bytes gets the same guarantee. Five attempts, twenty milliseconds apart, and a file failure comes
back as a returned exception rather than a thrown one.

## `ZeroZero.Config.Sections` — one document, several owners

Rebuilding a whole settings document from one type loses things, and the same three losses turned up
in two separate implementations: a section this build has no member for was discarded while the save
reported success; one unparseable value cost the whole document rather than its own section; and a
file that could not be read at all was replaced by defaults on the next ordinary save. **The section
store removes all three by construction rather than by rule.**

- **`SectionedSettingsFile`** hands out a **`SettingsSection<T>`** per top-level key. A section reads,
  updates and writes on its own; every other key in the file is carried through untouched, including
  keys nothing in this build knows about.
- **Every write re-reads the disk rather than memory**, so an edit made since the last read is part
  of what the write preserves, and a document that has become newer than this build understands is
  still not written over.
- **A section type must serialise to a JSON object**, and that is checked when the section is asked
  for, not at the first save.
- **The version key is written only when the document carries none**, and an existing one is never
  raised. Raising it is the migration's job, because sections belong to independently released
  components.

**Two keys differing only in case are refused.** A write that would leave the document carrying both
spellings fails, names both, and leaves the file exactly as it was — whether the pair would be two
sections, two members inside one, or two version keys. `SettingsSection<T>.ConflictingKey` lets a host
say why a page is empty. The rule catches case and only case: two genuinely different spellings are
two different members, and nothing can tell that one was meant for the other.

**`SettingsMigration`** writes a new document from an old one and never touches the source — not
renamed, not deleted, not even on success. Before reporting success it reads the new file back off
the disk and walks the old one again from scratch, checking duplicated keys by occurrence; if that
proof fails the new file is deleted and the outcome names what did not arrive. Comments are not
carried, and the result says so separately for a comment between values and one inside a value.

## `ZeroZero.Config.Watch` — a file edited outside the application

**`SettingsWatcher<T>`** watches the file, waits for the edits to stop, asks the store to re-read, and
raises `Changed` with the state before and after. A **`SettingsChangeClassifier<T>`** decides whether
the change was substantive: everything the exclusion list does not name counts, so a property added
later is weighed from the moment it exists.

- **It suppresses its own writes without a pause or a timer.** The examination asks what the store
  holds, tells it to re-read, and asks again; its own writes leave the two answers equal. Nothing
  depends on a notification arriving inside a window — which matters, because an atomic write reaches
  the file as a delete plus a rename, with no change notification on the target at all.
- **`Failed` is not only a failure channel.** When the file is well formed but nothing will reload
  from it — a section spelt in the wrong case, say — the watcher says so once, per distinct reason,
  rather than sitting silent. Clearing it is not announced, because the edit that clears it reports
  itself as a change.
- **It takes `ZeroZero.Config` and nothing else.** It reaches a store through three delegates, so it
  works over a section without knowing the document's shape. **It is the one assembly in the family
  its component's entry point does not carry**: a consumer that wants it adds a second reference of
  the same component.
- Notifications default to the thread the work happened on, which for the watcher is a timer thread.
  Pass a `NotificationContext` for anything that touches a window.

## Taking it

`ZeroZero.Config` is the whole of the plain store. `ZeroZero.Config.Sections` brings it with it. All
three assemblies release together under one tag and one number, all target `net10.0`, and none takes a
third-party package.
