**Every watcher failure now arrives on the notification context.** One behaviour fix, and a set of

**Patch.** No public member changes, nothing recompiles, and a consumer that already marshalled

## The failure that did not arrive where it was asked to

On 0.7.0 the watcher posted `Examined`, `Changed`, and the announcement it raises through `Failed`
when a well-formed file will not reload — and posted nothing else. **Every genuine failure was
raised straight from the watcher's own timer thread**: a store that threw, a dropped notification,
the watched folder going away, a subscriber that threw.

So a consumer that supplied a `NotificationContext` — which the guide directs for anything touching
a window — got what it asked for on the ordinary events and not on the failures. The same `Failed`
event reached that consumer on the interface thread or on a timer thread depending on why it fired,
and no correct handler can be written against that: a handler safe for the announcement touched its
interface off the interface thread the moment a real failure fired the same event.

The report now posts through the context like everything else, and the announcement no longer wraps
it. The raise stays outside the guard, so a `Failed` subscriber that throws is not then reported
through `Failed` again.

## What the guide said and the stores did not

A consumer on the sibling route reads these guides at the ref it pins, so a correction reaches it
only under a tag.

- **The case-conflict refusal is not uniform.** A section key and the version key are compared
  ordinally whatever serialiser is supplied, so those two always refuse. A member follows the
  serialiser, and the family default is case-insensitive, which makes that branch unreachable unless
  a case-sensitive serialiser is handed in. The case an adopter meets is a section key.
- **The document has no rule that the version key comes first**, and none that every other key holds
  an object. The guide stated both and contradicted itself two sections later.
- **Quarantine happens on every read**, so a `Reload` over a file that has gone bad quarantines it
  exactly as construction does.
- **The atomic replace is five attempts** — one try and four retries, not five retries.
- **The whole-file store canonicalises through its type**, so its next write drops comments, key
  order and any member the type does not declare. That is the one property to know before choosing
  it over the section store.
- **`SectionedSettingsFile.HasLoaded` is the write latch.** The whole-file store reports the same
  latch through nothing but a refused save.
