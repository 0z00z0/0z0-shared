**The sectioned store's own version key is `ConfigVersion`.** A settings document that declares
`Version` for the application's own purposes now reads and writes with nothing renamed on either
side, and both keys stand in the file untouched.

**Minor rather than patch.** No public member changes and nothing needs recompiling, but the key a
written document carries is different, and an installed document that already holds the old
lower-case key keeps it as an ordinary top-level key from now on.

## What a document looks like after this

| The document carries | What a write leaves |
|---|---|
| No version key | `ConfigVersion` stamped as the first key |
| `Version`, `version` or `VERSION` of its own | That key and its value untouched, `ConfigVersion` stamped beside it |
| `ConfigVersion` already | Nothing added; the declared number stands |
| A key differing from `ConfigVersion` in case alone | Nothing at all — the write is refused and the file is byte for byte as it was |

`DocumentVersion` reads the `ConfigVersion` key and nothing else, so a document whose only version
key is the old lower-case one reads null: the older, flat shape, which is read as it stands. The old
key is ignored, not removed — the store never touches a key it does not own.

## What a migration of an installed document produces

`SettingsMigration` replaces `ConfigVersion` and carries every other top-level key across. A file
written by 0.7.x carries the lower-case `version`, which is a different word rather than a different
case, so the new document holds `ConfigVersion` stamped first and that `version` immediately after
it, with its old value. Both are in the file, the store reads only its own, and `Carried` names the
old key among the keys that arrived.

## Why the collision it removes was worth a rename

Top-level keys are matched letter for letter, whatever the serialiser is set to; the serialiser's
case-insensitive matching binds a section's members and reaches no further. So the store's own key
and a document's own key collide only when they differ in case alone, and a key named `Version`
collided with a key named `version` on every single write while every section and value read
correctly.

An application that declares its own product version in its settings document therefore adopts this
component without renaming anything of its own. `ConfigVersion` is a word no application's own key
has met, and the two never come near each other.

## The refusal is returned, never raised

A refused write comes back in the `SettingsSaveResult` and is announced through `SaveFailed`. Nothing
is thrown out of the store, so an application that reads neither sees a write that appears to have
happened. A case clash does not clear itself either: every later write is refused the same way, for
as long as the key stands, and the person keeps changing settings that never reach disk. Read what
`Update` and `Write` return, or wire `SaveFailed`.
