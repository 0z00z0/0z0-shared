**The menu takes the taskbar's theme, and the host says which identity the shell holds the icon
under.** One behaviour change a consumer sees on screen and one property that corrects a claim the
host was making.

**Released** 2026-09-25

**Minor.** The menu's theme changes without being asked for, and one property is added. Nothing is
removed and no signature changes.

## The menu follows the taskbar

The menu opens on the taskbar, and Windows keeps two theme switches: one for the system surfaces
the taskbar is drawn on, and one for applications. An application that let the menu follow its own
theme drew a light menu against a dark taskbar whenever the two switches differed.

The host now draws the menu in the taskbar's own theme — read from the same registry value the
icon's stroke tone already came from — and applies it at every rebuild, so a theme changed while
the application runs is in the menu that opens next. An application that set the theme itself
before every open can stop.

**The mechanism is the process's menu mode, not a XAML property.** The menu is a native popup
rather than a flyout, and a theme set on the flyout or on the icon element leaves it light —
measured, in both themes, against the captured menu. What reaches it is `SetPreferredAppMode`
followed by `FlushMenuThemes`, both exported by ordinal from `uxtheme`. That mode is process-wide,
so it covers every Win32 menu the application shows, and on a Windows without the export the menu
stays as Windows draws it.

`MenuTheme` on `TrayHostOptions` names a theme outright for a host that wants one, and
`ElementTheme.Default` leaves the mode alone, which is what Windows decides from the apps theme.

## Two identities, and which one the shell holds

`TrayHost.Id` is what the application supplied, or what the host derived from the icon's name. It
is not what the shell holds the icon under: the notify-icon library derives an identity from the
icon's name and registers that instead, so a supplied identity reaches the shell nowhere.

Measured on Windows 11 build 26220.6682: `Shell_NotifyIconGetRect` answers `E_FAIL` for a supplied
`Id` and answers a rectangle for the identity the library registered.

`ShellId` is that identity, read from the library's own icon after `Start()` rather than derived
again, and null before then. Anything that asks the shell about the icon takes it. `Id`'s
documentation no longer claims to be the shell's.

## A trap recorded, with nothing to call for it

The shell keeps one entry per icon under the current user's `Control Panel\NotifyIconSettings`,
keyed on the identity `ShellId` names, and its `IsPromoted` value is what the taskbar settings page
writes to move an icon between the notification area and the overflow.

Measured on Windows 11 build 26220.6682, from a normal account: the value is written and reads
back, and the shell does not act on it — written while the icon was up and written before the icon
was created, the notification area's contents were unchanged both times, read through the
automation tree rather than from a screen grab. Whether a sign-in makes it take effect is untested.
So this release ships no call for it, and [`zerozero-tray.md`](../../zerozero-tray.md) records the
measurement instead.

## What a consumer has to change

Nothing is required. An application that set the menu's theme before every open should drop that
code, since the host now does it and the application's value would fight the taskbar's.

## Verifying it

The menu was captured in both taskbar themes through the repository's harness; the pictures are in
[`zerozero-tray.md`](../../zerozero-tray.md). The identities and the per-icon setting were measured
against the running shell, not read from its documentation.

## Unchanged

The icon file writer, the slot arithmetic, the stroke-tone decision, the render cache, the tooltip
discipline, click classification and every listener. Both tray assemblies release under the same
number.
