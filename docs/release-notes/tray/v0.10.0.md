**A tray application started at sign-in can wait for the taskbar and learn whether its icon was
created, instead of standing broken.**

**Released** 2026-10-10

**Minor.** Members are added. Nothing an application already calls behaves differently.

## Why

An application started by a logon task can run before Explorer has a taskbar. `Start()` then
throws "TryCreate failed.", and a process that carries on holds its single-instance lock with no
icon, so every later launch is refused until the process is killed by hand.

## Starting when the shell may not be ready

`await TrayStartup.StartAsync(host, options)` takes the place of `host.Start()`:

- It waits for the taskbar window for up to `ShellWait` (15 s), then renders the icon at the
  taskbar's own scale.
- It offers the icon to the shell up to `CreateAttempts` times (5), `RetryDelay` (1 s) apart.
- It returns a `TrayStartupResult` — `Created`, `ShellNeverAppeared` or `CreationFailed`, with the
  attempts, the time spent and the shell's last refusal — and never throws for the shell.
- After either failure the host is back to not started and can be started again. What the
  application does next is its own decision; ending the process is what releases the
  single-instance lock.

[`zerozero-tray.md`](../../zerozero-tray.md) has the wiring, the outcomes and a related trap: a
WinUI window opened before the shell is ready can throw from `AppWindow.IsShownInSwitchers`.

## What a consumer has to change

Nothing is required. An application that adopts the helper replaces `Start()` with the call above
and decides what a failed result means.

## Unchanged

`Start()` behaves exactly as before, including throwing when the shell refuses the icon. Both tray
assemblies release under the same number.
