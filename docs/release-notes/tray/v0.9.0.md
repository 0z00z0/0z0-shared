**An application can ask for the notification area instead of the overflow.** The shell keeps a
per-icon setting for it, and the host reads and writes it through the icon's own identity.

**Released** 2026-09-25

**Minor.** Members are added, and the icon registers under the identity the application supplies.

## Asking for a placement

`TrayHost.Placement` says where the shell draws the icon — the notification area beside the clock,
or the overflow behind the chevron — and is null while the shell keeps no entry for the icon, which
is the case until the icon has been created at least once.

`TrayHost.AskForPlacement(TrayIconPlacement)` writes the setting and registers the icon again. It
returns whether anything was written: false means the setting already reads as wanted, or the shell
keeps no entry the icon's identity alone picks out, and in neither case is the icon disturbed. What
the first write replaced is kept, and `RestorePlacement()` puts it back.

```csharp
host.Start();
if (settings.ShowBesideTheClock) host.AskForPlacement(TrayIconPlacement.NotificationArea);
```

**A placement takes effect at the next sign-in.** The shell keeps its own list of the notification
area for the length of a session and writes that list out rather than reading it back, so an
application that starts at logon gets the placement it asked for, and one switched on while the
session is running does not move until the next sign-in. Say that to the person choosing the
setting, or the setting looks broken.

## The rule about what is written

The decision is `TrayIconPlacements.Plan` in the plain assembly, apart from the writing:

- The entry is found by the icon's identity, never by the executable's path. The shell rewrites the
  path on an entry when the binary moves, and several entries can carry one path.
- Nothing is written when the entry already says what is wanted.
- Nothing is written when no entry carries the identity, or when more than one does — two
  installations this process cannot tell apart.

`NotifyIconSettings` carries the decision out and is public for an application that wants the
reading and the writing without the host.

## The icon's identity

The icon registers under the identity the application supplies as `TrayHostOptions.Id`, or under
the one the host derives from `TrayHostOptions.Name` when none is given. `TrayHost.ShellId` is that
identity after `Start()`, and the shell's per-icon settings are keyed on it.

**The shell treats a change of identity as a new icon**, so an application that supplies its own
identity registers under a different one once, and a person may have to place the icon where they
want it again. Keep the identity fixed across versions after that.

## What a consumer has to change

Nothing is required. An application that never asks for a placement behaves exactly as it did,
apart from the identity above.

## Unchanged

The icon file writer, the slot arithmetic, the stroke-tone decision, the render cache, the tooltip
discipline, click classification, the menu and its theme. Both tray assemblies release under the
same number.
