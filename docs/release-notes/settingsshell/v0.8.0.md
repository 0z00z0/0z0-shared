**The application chooses the colour behind the window.** Mica is tinted by Windows from the
wallpaper, so an active settings window takes a colour the application never picked and matches
nothing else it draws.

**Released** 2026-09-25

**Minor.** One optional member is added to `SettingsWindowSetup` and two small types come with it.
Nothing is removed and no signature changes.

## The backdrop's colour

`BackdropTint` on `SettingsWindowSetup` names the colour, one for each theme, and the window
follows its own live theme between them:

```csharp
BackdropTint = new BackdropTint
{
    Light = BackdropColour.Parse("#F3F3F3"),
    Dark  = BackdropColour.Parse("#1B1B1F"),
},
```

An application sets it to the colour of its own main window, so the two windows match.

`BackdropColour` is three channels as plain numbers, with `Parse` taking `#RRGGBB`. Plain numbers
rather than a platform colour type, so the rule that decides which colour a window opens with is
pinned by a test that never loads the XAML runtime.

## The default is what it was

Left unset, the window keeps the markup's own Mica in the `BaseAlt` kind, which Windows tints from
the wallpaper. The resolution answers nothing for either theme when nothing is supplied, and the
window then replaces no backdrop. That is a guard rather than a description: the markup test that
pins the backdrop now pins this beside it, and was broken once to prove it fails for a test reason.

## What a consumer has to change

Nothing. A window that supplies no tint renders exactly as it did.

## Verifying it

Proved by running: the same window opened with and without a colour through the repository's
harness, which takes `--tint <#RRGGBB>` under `--settings`, and the window's own composited bitmap
captured each time.

## Unchanged

The chrome, the pane, the page host and its scroll viewer, the section lifecycle, the placement
arithmetic, the footer, Escape, and `FitToPages`.
