A documentation release carrying one small code change. **No API change** — no public signature is
added, removed or altered. What it carries is a measured account of what a host's branding actually
reaches on the panel, which is what a consumer needs *before* starting rather than after, and a
consumer that pins tags reads the guides at the tag it pinned. `v0.2.1` was cut for the same reason.

## What a host's branding reaches — before branding anything

**A host branding the panel gets the module's own surfaces and the toolkit's cards and expanders,
matching each other. What stays stock is the WinUI control parts** — combo boxes, text boxes, the
password box, buttons, the toggle switch, the info icons and the device-id dialogue's chrome.

Two override sets produce the branded half, and a host that brands its other pages already declares
the second one: the module's six keys for the panel's own surfaces, and the application's own
override of the toolkit's semantic brushes — `CardBackgroundFillColorDefaultBrush` and
`TextFillColorPrimaryBrush` — for the cards.

Measured on an installed, rendered build: the application's card override reached every toolkit
`SettingsCard` **including those inside the panel**, at exactly the studio ground — flat and opaque,
strokes matching at 2 px — while a combo box on the same page kept stock values until its own
control keys were declared. `MqttPanelCardBackgroundBrush` took the same application override, so
the Status band and the toolkit cards beside it measure identically.

| Surface | What reaches it |
|---|---|
| Section headings | `MqttPanelHeadingBrush` |
| The Status block's ground | `MqttPanelCardBackgroundBrush` |
| The Status block's labels | `MqttPanelBodyBrush` |
| Row descriptions, hints, status values and the device-id echo | `MqttPanelSecondaryBrush` |
| The applied, unapplied and saved markers | `MqttPanelAccentBrush` |
| The typeface everywhere the panel styles text, the value text inside the fields included | `MqttPanelFontFamily` |
| Every `SettingsCard` and `SettingsExpander`, ground and header | The application's toolkit semantic brushes |
| The combo boxes, text boxes, password box, buttons, toggle switch, info icons and dialogue chrome | Each control's own keys, and nothing else |

Validation errors and the section rules resolve platform keys by intent, so a refused value reads as
failure in the host's own language rather than in the panel's accent.

**This is separate from the placement rule `v0.2.1` carries.** A misplaced key set changes *nothing*
and the panel renders wholly stock;
[Where an override goes](https://github.com/0z00z0/0z0-shared/blob/v0.3.3/docs/zerozero-mqtt.md#where-an-override-goes)
is still the first thing to re-read when nothing at all arrived.

## The decision a consumer actually has: stock control chrome, or 266 keys

**A control takes its colours from its own keys** — `ComboBoxForeground`, `TextControlForeground`,
`ButtonBackground` and their per-state siblings. Those are what a control template looks up at run
time, so declaring one as an immediate entry of `Application.Resources` does reach the control. It
is the one dependable lever, and there is a key per control per state.

Counted against WinUI's `Default` dictionary, for exactly the controls this panel renders: **266
live brush keys**, spread across the check box, the combo box and its items, the toggle switch, the
text controls, the expander, the button, the toolkit card and the content dialogue. That number is
why the module does not carry them, and why a consumer should have it before deciding to. A panel
key set duplicating the control keys would brand this one panel and leave the rest of the
application behind; an application that wants branded dropdowns and fields declares the control keys
in its own resources, where they reach every page it has.

So the choice is not whether to brand the panel. It is whether to accept stock control chrome —
which is what every other WinUI page in the application shows too — or to take on the control key
sets.

### Why the toolkit follows and the controls do not

**When a dictionary is parsed decides it.** The toolkit's dictionary loads on first use, after the
application's own entries exist, so its aliases resolve against them. WinUI's own dictionary is
parsed at startup, before an application's entries exist, and its aliases are frozen at that moment.

That is why overriding the shared semantic brushes reaches a WinUI control **not at all**.
`ComboBoxForeground` is a `StaticResource` alias to `TextFillColorPrimaryBrush`, resolved inside
WinUI's dictionary as it is parsed; replacing `TextFillColorPrimaryBrush` afterwards leaves the alias
pointing where it already pointed. Overriding the paired `*Color` key misses for the same reason —
the brush binds its colour with `StaticResource` as well. Accent-derived brushes are the one partial
exception, binding with `ThemeResource`, so replacing an accent colour does propagate. An accent that
carries and toolkit cards that repaint are what make the semantic brushes read as a general route
when they are not one.

## The device-id dialogue's secondary text is reachable at last

Two lines in the device-id dialogue — the prompt above the field and the sanitised-id echo below it
— carried a hard-coded `0.7` opacity. An opacity is a tone no theme key can reach, so a host that
rebranded the panel could not rebrand those two lines. Both now take the panel's own secondary text
style and follow `MqttPanelSecondaryBrush` and `MqttPanelFontFamily` with everything else.

Measured against the dialogue's ground: **6.29:1 to 6.19:1 in light, 7.70:1 to 9.09:1 in dark.** This
is the release's only code change, and the only thing in it a consumer can observe at run time.

## Contrast, measured in both themes

Every text tier the panel renders, rendered and sampled against the ground it actually sits on —
which for a card is the composite of the card's translucent fill over the page.

| Tier | Light | Dark |
|---|---|---|
| Section heading, 15 px | 15.68 | 16.29 |
| Card header, 14 px (toolkit) | 16.65–17.08 | 9.44–14.16 |
| Status label, 14 px — body key | 16.65 | 14.16 |
| Descriptions and status values, 11 px — secondary key | 6.03–6.19 | 5.52–9.09 |
| Applied and unapplied markers, 11 px — accent key | 9.32–10.25 | 5.06–8.73 |
| Validation error, 11 px | 5.47 | 6.97 |
| Device-id dialogue, body 14 px | 17.22 | 14.16 |
| Device-id dialogue, secondary 11 px | 6.19 | 9.09 |

**Every tier clears the 4.5:1 accessibility threshold in both themes. The floor is 5.06:1** — the
accent marker on a Broker card in dark.

**A Mica backdrop moves no ratio by more than 0.06.** WinUI clamps the backdrop tint hard toward the
fallback base colour: a light page ground measures `#F1F3F9` against the flat theme's `#F3F3F3`. A
panel measured over a flat page background is therefore measured for Mica too, and that holds for
the surfaces with no ground of their own — the section headings and the translucent card fills.

**No default colour changed.** These are `v0.3.2`'s defaults, measured for the first time rather
than adjusted to reach a figure.

## Pre-1.0 — what this patch means for a pin

While the major version stays `0`, a **minor** bump may break the API and a **patch** never does.
This one adds no public member and removes none, so raising a pin from any `v0.3.x` to `v0.3.3`
cannot change what an application compiles. It changes one thing an application can observe: the
two secondary lines in the device-id dialogue now follow the panel's theme keys, where before they
were a fixed opacity over the platform foreground.

**Raising the pin is not by itself enough for a consumer that builds locally.** The project reference
resolves through `ZeroZeroSharedDir`, which defaults to the sibling working tree; nothing reads the
pinned-ref file to decide which sources compile. Check the sibling clone out at `v0.3.3` — the pin
file records the intent, the working tree decides the build. The MQTT guide's
[Take the reference](https://github.com/0z00z0/0z0-shared/blob/v0.3.3/docs/zerozero-mqtt.md#1-take-the-reference)
states this in full.

## Everything else

Unchanged from `v0.3.2`: the seven source projects and their one-way dependency, every public
signature, the entity model, the device document, identity, the ledger's shape on disk, the
encryption model, the endpoint sweep, the reconnect ladder and every other behaviour of the panel.
`v0.3.2`'s notes remain the account of the connect storm and the eviction paths, `v0.3.0`'s remain
the account of what that release changed, and `v0.1.0`'s **Differences from an earlier shape**
tables remain the migration reference.

## Requirements

.NET 10 SDK. Windows 10 1809 (build 10.0.17763) or later with the Windows App SDK for the WinUI
assemblies; `ZeroZero.Brand.Core`, `ZeroZero.Config`, `ZeroZero.Mqtt` and `ZeroZero.Mqtt.Discovery`
are plain `net10.0` and portable in isolation. The MQTT module requires an MQTT 5.0 broker and, for
discovery, Home Assistant 2024.11.0 or later.

## How to consume it

There is no NuGet feed: neither `ZeroZero.Brand.WinUI` nor `ZeroZero.Mqtt.WinUI` can be packed, so
this release is the tag and these notes — which is all a `ProjectReference` on a pinned checkout
needs. Pin `v0.3.3` as the `ref` of the consumer's second `actions/checkout`, or as
`--branch v0.3.3` on a sibling clone.
[Pin a tag](https://github.com/0z00z0/0z0-shared/blob/v0.3.3/README.md#3-pin-a-tag) in the README
carries both shapes, the MSBuild property that lets CI redirect the reference, and the item-glob
exclusions a workspace-subfolder checkout needs.

The theming statement in full, with the per-control key counts and the screenshots the surfaces were
read off, is
[What a host's branding reaches](https://github.com/0z00z0/0z0-shared/blob/v0.3.3/consume-mqtt-settings-panel.md#what-a-hosts-branding-reaches)
in the consumption guide.
