**The watchdog task belongs to the component.** Additive: the logon task and every type around it
keep their shape.

**Released** 2026-09-24

## Why it lives here

A watchdog is the one backstop against any way a process can die, so an application whose session
blocks input or the network depends on it. Two applications keeping their own copy of it drift, and
the copy that is wrong is the one nobody is watching.

## Added

- **`WatchdogTask`** — the task by name. `Ensure()` writes it where it is absent or has drifted,
  leaves a correct one alone, and never throws: it runs at application start, where a throw would
  take the application down over the very task that exists to bring it back. The constructor checks
  its arguments and nothing else — the scheduler connection, the executable path, the marker path
  and the two task names are resolved inside `Ensure()`, where a refusal is the `Failed` outcome.
  `Delete()` for the installer's uninstall. `Hold` is the record of a deliberate exit and
  `Restarts` the bound below.
- **`WatchdogTaskOptions`** — name, the logon task's name, description, executable, the relaunch
  argument, what started this copy of the application, the three probes' timing, the hold marker's
  path, the application's check on where it is installed, and the log sink.
- **`WatchdogStartCause`** and **`WatchdogRestartLimiter`** — the bound on the probe's own restarts.
- **`WatchdogHold`** — `Hold()`, `Release()`, `IsHeld`. A file, because the two sides never share a
  process: the exit is written by the application on its way out and read by the copy the scheduler
  starts afterwards.
- **`WatchdogEnsure`**, **`WatchdogEnsureResult`** and **`WatchdogEnsureOutcome`** — the decision
  over delegates, testable with no scheduler. `Skipped`, `AlreadyCorrect`, `Registered`, `Stopped`,
  `Failed`.

## What the task looks like

The same principal and power-safe settings as the logon task, with `StartWhenAvailable` on, and
three triggers: a repeating one every five minutes by default; one five seconds after the
workstation unlocks; and one fifteen seconds after Power-Troubleshooter event 1, which the machine
writes when a resume has completed. The unlock and resume probes exist because a process killed
while the machine was locked or asleep would otherwise stay down for a whole interval of active
use.

## The restarts are bounded

A probe that starts an application which cannot run would otherwise start it every five minutes for
ever. After three probe-started runs inside fifteen minutes, none of which stayed up two minutes,
the task is disabled and the outcome is `Stopped`; one line says so and nothing repeats it.
Probing resumes when a person starts the application — that start clears the count, and a disabled
watchdog is a deviation the same call repairs.

The application answers one question for this: `StartCause`, which is required, and which the
relaunch argument the options already carry already tells it. The count lives beside the hold
marker, because the process keeping it is the one that keeps dying.

## The record of a deliberate exit expires, and says whether it worked

The marker carries the moment it was written, and one older than thirty days counts as absent: a
marker left behind by a clear that failed would otherwise keep the application down for the life of
the installation. A marker that is there but cannot be read counts as **held** — starting the
application against the person's choice costs more than leaving it down — and both cases are
logged.

`Hold()` and `Release()` each say whether they worked, so a caller can tell the person that the
exit was not recorded rather than finding out when the application comes back by itself.

## Two tasks of one name are refused

Where `LogonTaskName` is given and matches the watchdog's own name, `Ensure()` reports `Failed`
naming the collision and writes nothing — so the logon task registered under that name keeps the
person's choice about starting at logon instead of being replaced by a probe.

## What the drift read compares

The settings, the principal and the action are checked by the same code as the logon task's, so a
check added for one is not missed by the other; that is where the watchdog's process-priority check
comes from. Its own: the account the task runs as and the account its unlock trigger names, the
repeating probe's interval, repetition duration, start boundary and enabled flag, the unlock and
resume delays, `StartWhenAvailable`, and the task's enabled flag. A mismatch on the account is
repaired — one account owns the task at a time on a machine several people sign in to.

**Neither a path nor an account name appears in a drift line.** That list goes out at information
level on every start, and where the application is installed and who is signed in are not the log's
business. The install path is written once, at error level, when the write fails.

## Where it differs from the logon task, deliberately

- **An absent watchdog is written.** The logon task's absence is the person's choice and `Repair`
  respects it; the watchdog is the application's own backstop and `Ensure` creates one.
- **A disabled watchdog is repaired**, for the same reason — except where the restart bound
  disabled it.
- **Nothing about the person's logon choice is consulted.** `Ensure` runs on every start regardless.

## What stays with the application

The single-instance gate that makes a probe finding a live process exit at once; deciding that an
exit was deliberate and calling `Hold()`; saying which kind of start this is; the check on where the
application is installed, passed as `RegisterWhen`, because a task pointing at build output starts
stale binaries for as long as it survives; and removing both tasks at uninstall.

## What a consumer on 0.8.0 gets

Nothing it had changes. An application still keeping its own watchdog can adopt this at its own
pace; until it does, the two definitions have to be kept in step by hand, which is the state this
release exists to end.

The logon task's registration line carries no account name, and a repair that fails writes the
executable path at error level. Nothing a consumer compiles against moves.
