**A repair of an application that stays resident always reported verification failed.**

**Minor.** `StartupTaskRunResult` gains a fourth positional parameter, so anything that constructs
or deconstructs one recompiles. Nothing else changes shape.

## What a consumer on 0.7.2 gets

`Repair()` with `VerifyByDemandStart` proved a rewritten task could run by demand-starting it and
asking whether the run succeeded. A run succeeded only if the started program exited with zero
inside the wait — and a tray application never exits.

So every repair of such an application's logon task spent the full thirty seconds and then reported
`VerificationFailed`, whether or not a copy was already running. Measured through the repair both
ways: 30.1 s with an instance alive, 30.1 s with nothing running. The control, the same repair
against a program that exits at once, reported `Repaired` in 4.0 s.

Anything built on that outcome — a tray state, a health line, a decision to warn the user — was
told the repair had failed on every start, for every application the component was written for.

## What it does now

A run that ends is settled exactly as before: state `Ready`, the result held for the 500 ms settle
where it is zero, and `Succeeded` on a zero. What changes is the case where nothing settles. One
further reading is taken once the wait is over, and a task still running then, whose run time has
moved past the reading taken before the start, counts as a program that started.

The scheduler reports the task as running in two shapes and both count: `0x41301`, where it
launched the program, and `0x800710E0`, where it refused the start because an instance was already
alive. The second is what a resident application's repair of its own logon task meets, since the
definition's multiple-instance policy is ignore-new.

There is no early return while the task runs. A program that ran six seconds and then exited with a
failure reads exactly like one that was about to exit with zero, so only the end of the wait
separates them.

## What is unchanged, and proved to be

- A queued run is still not a successful one. Queued is not running, so the fix in 0.7.2 stays
  closed.
- A task pointing at an executable that does not exist is still a run that happened and failed. It
  never reaches the running state at all: the scheduler returns it to ready carrying `0x80070002`,
  measured at 23 ms.
- A run that ends non-zero still fails.

## The wait, and what shortening it costs

`StartupTask.VerificationWait` drops from 30 s to 15 s. The whole wait is spent wherever the started
program stays resident, on the start-up path of the application being repaired, so it is worth
shortening — but it is not free.

**The scheduler holds a finished run in the running state for seconds after the program is gone.**
Measured from the start to the terminal reading: 4.0 to 8.1 s over ten runs on an idle machine; with
a spinning job on every core, a median of 6.1 s over twenty runs and a worst case of 48 s. Through
that window the state, the running-instance count and the result code read exactly as they do for a
program that is genuinely up.

The wait's length is therefore what decides how often a program that started and then failed is
counted as a start. Fifteen seconds is about twice the worst idle measurement, and covered 17 of the
20 loaded runs. The check has never been able to speak about a program that starts correctly and
fails later, and it still cannot.

Verification is paid once per definition change, not on every start: a task that already matches is
never rewritten and never verified.

## What the verification leaves behind

Nothing is stopped. Where the scheduler refused the start, it launched nothing to stop; where it
launched the program, the copy is a legitimate one, and the two cases read the same at the deadline,
so stopping on that reading would risk killing a running application.

## Added

- `StartupTaskRunResult.StillRunning` — the task was running when the wait ended, having been
  started within it. `Succeeded` is now `StillRunning` or a run that ended with zero.
- `StartupTask.AlreadyRunningResult` — the `0x800710E0` the scheduler records when it refuses a
  start because an instance is already alive, beside the `NeverRunResult` and `RunningResult`
  already named.
