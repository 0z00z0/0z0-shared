**A repair could report success on a task whose executable failed.**

**Patch.** Two public constants are added and nothing is removed, so nothing recompiles.

## What a consumer on 0.7.1 gets

`Repair()` with `VerifyByDemandStart` proves the task can start its executable by demand-starting
it and asking whether the run succeeded. That check could answer yes about a run that failed.

The result is that start-with-Windows stops working, the repair says it fixed it, and nothing in
the log or the outcome says otherwise. Anything a consumer builds on the repair's outcome — a
tray state, a health line, a decision not to warn the user — is built on that answer.

## What was wrong

The demand start stopped waiting as soon as the scheduler showed a new run time and a state other
than "running", and read the result code at that instant. The scheduler settles a run's state
before it settles the run's result, and between the two it writes the code that means the launch
succeeded: zero. A read landing there is handed the launch's zero rather than the executable's
exit code, and a run counts as succeeded when its code is zero.

The gap is open wider while a run is only queued. The last run time has already moved on, the
state is not "running", and the result still holds the previous run's — measured at more than a
second before the executable even starts.

## What it does now

The run time, the state and the result are read together at every poll rather than the result once
at the end. A run is over only at state `Ready`; `0x41301` and `0x41303` are never a result; any
other non-zero code is the executable's and is final at once; and a zero is held for
`StartupTask.ResultSettle`, 500 ms, and believed only if it survives.

Measured worst case between the state settling and the result settling is 72 ms, so the settle is
about seven times it. It is paid only where the result is zero, and the wait the caller gave stays
a hard bound: a run that ends with zero inside its last 500 ms is now reported as not ended rather
than as succeeded.

Under a load that made the previous wait report a failed run as successful, a hundred demand starts
reported none.

## Added

- `StartupTask.RunningResult` — the `0x41301` the scheduler reports while a run is in flight,
  beside the `NeverRunResult` that was already named.
- `StartupTask.ResultSettle` — how long a zero is held before it is believed.
