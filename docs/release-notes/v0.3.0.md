**Breaking.** Three members of `DiscoveryPublisherSetup` are now `required`, so a consumer that
omits one no longer compiles. Each of them was a silent, total failure when left out, and none of
them announced itself: the build was green, nothing warned and nothing logged.

## The breaking change: the wiring cannot be forgotten

`SetChannelsAsync`, `SetCommandTargets` and `Groups` were optional. Omitted, the publisher went on
rebuilding the discovery document correctly while never handing the rebuilt channel set to the
connection, never handing it the command targets, and never reading the group state:

- **Entities appear on the receiver and stay unknown for ever.** The document names them; the
  connection has no channel to publish any of them on.
- **Every command is refused as unrecognised.** The document declares the command topics; the
  router has no target to resolve them to.
- **A group toggle writes to settings and changes nothing on the wire.** The panel shows the new
  state and the published surface does not move.

All three now have to be written down. `IsConnected`, `TopicRoot`, `Device`, `Origin`, `Entities`
and `Ledger` were already required, and this puts the wiring on the same footing.

### What a consumer must do

**A consumer that already wires all three needs no change.** That is the documented shape, and it
is what the guide's step 5 has always shown.

A consumer that omits any of them adds it, and the compiler names which:

- `SetChannelsAsync = (channels, ct) => connection!.SetChannelsAsync(channels, ct)`
- `SetCommandTargets = targets => connection!.SetCommandTargets(targets)`
- `Groups = groups`, or `Groups = null` for a consumer that declares no publish groups.

`Groups = null` is a first-class answer and gives up nothing: a consumer with no groups declares it
and the pass treats every entity as always published.

### The named opt-out, for a publisher that drives no connection

The two hand-overs are not merely paperwork, so they are not satisfied by a bare `null`. Where the
published surface is genuinely fixed for the life of the process — or where there is no connection
at all — the new `DiscoveryWiring` class carries the opt-out, and its name is the declaration of
what is being given up:

- `SetChannelsAsync = DiscoveryWiring.NoChannelHandover` — the connection keeps the channels it was
  declared with, so an entity set, a group toggle or an `Include` that changes at runtime no longer
  changes what is published: an entity announced later never has its topic written, and one
  withdrawn goes on publishing.
- `SetCommandTargets = DiscoveryWiring.NoCommandHandover` — the router keeps the targets it was
  declared with, so a command addressed to an entity announced later is refused as unrecognised,
  and one addressed to an entity since withdrawn is still acted on.

Silence is what the change removes, not flexibility.

## A bare channel now says "no reading" rather than emptying its topic

`MqttChannel` carries its own `NoValuePayload`: what goes out when the channel's payload function
hands back nothing. **It defaults to `MqttChannelPayload.None` — the literal `None` — where the
connection previously emptied the topic.**

This is a behaviour change for a consumer using `ZeroZero.Mqtt` alone. The substitution existed only
in the entity layer, so a headless consumer declaring its own channels got the behaviour measured
against a live receiver as wrong: a zero-length payload is ignored on `sensor`, `binary_sensor`,
`switch`, `number` and `select`, the receiver goes on showing the last value it saw, and the stale
reading stands indefinitely.

**The safe answer is the default**, because the failure it prevents is silent and unbounded while
the failure it can cause is visible at once. A channel where an empty payload is the right answer
declares `NoValuePayload: ""` and gets exactly the old behaviour — right for a text value, and for
a receiver that reads a cleared retained topic as no value.

**A consumer on `ZeroZero.Mqtt.Discovery` is unaffected.** The entity layer sets the channel's
no-value payload per platform, as it already set the payload itself: `None` on the five platforms
that ignore an empty payload, and empty on `text`, where an empty string is a value. `MqttText`
still empties its topic, byte for byte as before.

- **The guide states the wiring obligation and the channel's no-value payload** where each belongs:

  consumer using the core alone.

## Pre-1.0 — what this minor means for a pin

While the major version stays `0`, a **minor** bump may break the API and a **patch** never does.
This one breaks it on purpose. Raising a pin from `v0.2.1` to `v0.3.0` fails to compile in a
consumer that omitted any of the three members, which is the whole point: the omission was
undetectable at runtime and is now impossible at build time.

The behaviour change in the second section reaches a consumer that declares channels directly on
`ZeroZero.Mqtt`. A consumer on the entity layer sees no change on the wire.

## Everything else

Unchanged from `v0.2.1`: the six shipping assemblies and their one-way dependency, the entity model
and its component types, the device document, identity, the ledger's shape on disk, the encryption
model, the endpoint sweep and every behaviour of the panel. `v0.1.0`'s **Differences from an earlier
shape** tables remain the migration reference.

## Requirements

## How to consume it

There is no NuGet feed: neither `ZeroZero.Brand.WinUI` nor `ZeroZero.Mqtt.WinUI` can be packed —
both compile XAML to binary form, and the panel additionally indexes a `.resw` into a `.pri`, none of
which `dotnet pack` carries — so this release is the tag and these notes — which is all a `ProjectReference` on a pinned checkout needs. Pin `v0.3.0` as the
`ref` of the consumer's second `actions/checkout`, or as `--branch v0.3.0` on a sibling clone.
[Pin a tag](https://github.com/0z00z0/0z0-shared/blob/v0.3.0/README.md#3-pin-a-tag) in the README
carries both shapes, the MSBuild property that lets CI redirect the reference, and the item-glob
exclusions a workspace-subfolder checkout needs.

The wiring is
[Compose the connection](https://github.com/0z00z0/0z0-shared/blob/v0.3.0/docs/zerozero-mqtt.md#5-compose-the-connection)
in the interface guide, and the channel's no-value payload is in
[Measured behaviour that contradicts the obvious implementation](https://github.com/0z00z0/0z0-shared/blob/v0.3.0/docs/zerozero-mqtt.md#measured-behaviour-that-contradicts-the-obvious-implementation).
