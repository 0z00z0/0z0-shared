A documentation-only release. **No API change, no behaviour change and no code change** — the
assemblies are `v0.2.0`'s. It exists because the correction it carries prevents a silent failure,
and a consumer that pins tags reads the guides at the tag it pinned, so a fix left on `main` does
not reach it.

## The correction: where a theme override goes

**This concerns a consumer that overrides the panel's theme keys.** A consumer that leaves all six
alone is unaffected and needs nothing from this release.

`v0.2.0` said the keys win when "declared directly in `Application.Resources`". That reads as
*somewhere in the application's resources*, and the first consumer to brand the panel placed them
inside `Application.Resources.ThemeDictionaries` — beside its own per-theme palette, which is where
they look like they belong. That is one level below what the panel resolves, so **all six keys fell
back to the module's stock defaults**. The build was green, nothing warned, nothing logged, and the
effect was total rather than partial: the panel rendered in the stock WinUI theme beside pages
carrying the host's own, which reads as the module ignoring the host's branding rather than as a
misplaced declaration.

Both guides now state the placement as a rule and show it rather than describe it:

- **The six keys are immediate children of `Application.Resources`**, at the level of that
  dictionary's own entries — shown as a copyable `App.xaml` fragment. The module adds its defaults
  to `Application.Resources.MergedDictionaries` when the first panel is constructed, and a
  dictionary's own entries outrank everything it merges.
- **The theme variation belongs to the colour each brush resolves, not to where the brush is
  declared.** That is how the module's own defaults are built, and it is what lets light and dark
  differ while the keys stay at the one level the lookup reads.
- **Two placements silently do nothing.** Inside `Application.Resources.ThemeDictionaries` is below
  the lookup. Inside a dictionary the application merges itself is merged before the module's own
  and therefore loses to the default it was meant to replace.
- **What the failure looks like:** every key to stock, no warning, no build error, and a panel that
  appears to ignore the host's theme entirely.
- **How to catch it:** sample the panel's heading and the application's own heading in the same
  frame — an override that arrived makes the two identical, byte for byte. This sits beside the
  contrast measurement `v0.2.0` already documented, and the two answer different questions: a key
  that fell back reads as the module's own default rather than the host's, which the measurement
  separates from a palette that is merely poor.

Measured on the corrected placement: the panel's heading sampled byte-identical to the application's
own heading in the same frame, where before it sampled plain white; the status values measure
11.07:1 against the branded ground and the labels 14.47:1.

## Pre-1.0 — what this patch means for a pin

While the major version stays `0`, a **minor** bump may break the API and a **patch** never does.
This one changes no code at all. The files that differ from `v0.2.0` are the two guides, the
README's pinning examples and its statement of when a tag is cut, the declared version and these
notes — so raising a pin from `v0.2.0` to `v0.2.1` cannot change what an application does.

The README also now says tags are cut on a consumer-visible **change** rather than on a
consumer-visible **API** change: the guidance a consumer builds against counts, because a correction
to it reaches a consumer pinning tags only when a tag carries it.

## Everything else

Unchanged from `v0.2.0`: the six shipping assemblies and their one-way dependency, every public
signature, the entity model, the device document, identity, the ledger's shape on disk, the
encryption model, the endpoint sweep and every behaviour of the panel. `v0.2.0`'s notes remain the
account of what that release changed, and `v0.1.0`'s **Differences from an earlier shape** tables
remain the migration reference.

## Requirements

.NET 10 SDK. Windows 10 1809 (build 10.0.17763) or later with the Windows App SDK for the WinUI
assemblies; `ZeroZero.Brand.Core`, `ZeroZero.Config`, `ZeroZero.Mqtt` and `ZeroZero.Mqtt.Discovery`
are plain `net10.0` and portable in isolation. The MQTT module requires an MQTT 5.0 broker and, for
discovery, Home Assistant 2024.11.0 or later.

## How to consume it

There is no NuGet feed: `ZeroZero.Brand.WinUI` cannot be packed, so this release is the tag and
these notes — which is all a `ProjectReference` on a pinned checkout needs. Pin `v0.2.1` as the
`ref` of the consumer's second `actions/checkout`, or as `--branch v0.2.1` on a sibling clone.
[Pin a tag](https://github.com/0z00z0/0z0-shared/blob/v0.2.1/README.md#3-pin-a-tag) in the README
carries both shapes, the MSBuild property that lets CI redirect the reference, and the item-glob
exclusions a workspace-subfolder checkout needs.

The theming guidance is
[Where an override goes](https://github.com/0z00z0/0z0-shared/blob/v0.2.1/docs/zerozero-mqtt.md#where-an-override-goes)
in the interface guide, and the same rule shortened in
[`consume-mqtt-settings-panel.md`](https://github.com/0z00z0/0z0-shared/blob/v0.2.1/consume-mqtt-settings-panel.md#theming).
