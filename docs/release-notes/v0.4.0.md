**The two collapsed sections of `MqttSettingsPanel` now summarise the configuration instead of
describing themselves**, and the panel's own copy has been reworded where it described the
implementation rather than what a user experiences. **A consumer holding screenshots of the panel,
or a translation of its strings, is affected** — see below for the exact keys.

**Minor rather than patch.** Six public members are added, and three string keys are removed or
renamed. Nothing is removed from a type's signature, so an application that only *renders* the panel
recompiles unchanged; an application that *translates* it has entries that silently stop being read.

## A closed section now says what is configured

Both groups open closed, and both previously carried a fixed description that restated the heading
above them — "How the broker is reached" under **Broker**, "Which entities are announced" under
**What to publish**. Neither said anything the heading had not.

Each now carries a line composed from live state, so the configuration is readable without opening
the group.

### The Broker line marks a detected value as detected

It carries the host and then the port, transport and encryption, separated by `·`. Each of the three
has **three** readings, not two:

| The field is | The line shows | Example |
|---|---|---|
| set by hand | the value, unqualified | `8883` |
| on Automatic, with a live connection behind it | the value in force, marked | `8883 (detected)` |
| on Automatic, with nothing found yet | the instruction itself | `Automatic` |

**The marking is the point.** On a typical installation only the host is set and every other field is
left on Automatic, so a summary of what is merely *configured* reads `host · Automatic · Automatic ·
Automatic` — which looks like information and is not. Showing the resolved value makes the row worth
reading; marking it keeps the instruction-versus-outcome separation the rest of the panel relies on,
where the dropdowns hold the instruction and the Status rows hold the outcome. The third state
exists so a fresh installation shows the word `Automatic` rather than an empty parenthesis.

**A detected value is shown only while the link that found it is up.** Once the connection drops, the
same value is a reading from an earlier moment, and printing it unqualified would be the error the
marking exists to prevent arriving by another route — so each Automatic field falls back to the bare
instruction. A blank host reads `No broker set`.

**Where the address settles the scheme, the address wins.** A WebSocket front door on a port whose
scheme is fixed by convention reads `encrypted` whatever the encryption switch says, and the port it
is read from is the detected one when the port itself is on Automatic. Anything else would put a
false statement about the wire beside a Connection row asserting the opposite.

**The line carries the saved values, not the ones being edited.** The unapplied marker sits beside
the section heading, outside the group, and says when the two differ.

### The publish line is a count

`2 of 3 switched on`, and `Nothing to switch on or off` for a consumer that declares no groups. A
count rather than the group names, because the module declares no group of its own and a consumer
may declare any number: a list of names grows without bound where a count stays one short true fact.
The entities behind the groups are never counted — the panel is not shown the entity set, so a
number for it could only be invented.

## The panel's copy describes what a user experiences

Every string the module owns was read against one question: does it describe what the user
experiences, or what the code does. Five are reworded.

**The Broker section's info text** described the implementation throughout: fields were "staged
locally", the connection was remade "once per edit session rather than once per keystroke", and
Automatic values were "found by probing" when a field "settles". The two questions a user actually
has are *when does what I typed take effect* and *does opening this page touch the broker*. It now
answers those and nothing else, and says that opening the page never starts a check.

**`InfoBrokerInUse`** said the fields below were "staged"; it now says they are being edited.
**`InfoConnection`** said a value was "found by probing" and could "settle" on clear text; it now
says it is found by trying the host and can end up in clear text. **`InfoStatus`** said the two ages
"re-read themselves"; they now keep counting up. **`InfoTransport`** said Automatic tries "a plain
socket" first; it now says TCP, which is what the dropdown beside it offers.

**Kept deliberately:** *host*, *port*, *transport*, *broker*, *topic*, *listener* and *endpoint* —
protocol and broker-administration words a user configuring MQTT meets in the wild, and *field*,
which is a form's own vocabulary. **Removed as the module's own machinery:** *probe*, *sweep*,
*channel* and *socket* standing alone, plus *staged*, which is borrowed from version control and
describes neither. A test now holds the line: every built-in string is checked against a list of
implementation words, and no user-facing string may contain one.

## What a consumer has to check

**Screenshots.** Every panel image in this repository is recaptured. A consumer that embeds its own
screenshots of the panel has ten images' worth of copy that has moved.

**Translations.** A key that changes name is a translation that silently stops being read: the lookup
finds nothing, answers null, and the built-in en-GB stands with no error anywhere.

- `PortAutomatic` is renamed **`OptionAutomatic`** — it names the Automatic entry in three dropdowns,
  not just the port's.
- `DescBroker` and `DescPublish` are **removed**. The lines they filled are composed now.
- Seven keys are **added**: `SummaryBroker`, `SummaryBrokerNotSet`, `SummaryDetected`,
  `SummaryEncrypted`, `SummaryNotEncrypted`, `SummaryPublish`, `SummaryPublishNoGroups`.
- Five keys carry **new text**: `InfoBroker`, `InfoBrokerInUse`, `InfoConnection`, `InfoStatus`,
  `InfoTransport`.

`SummaryBroker` is `{0} · {1} · {2} · {3}` — host, port, transport, encryption — and a translation
may reorder it. `SummaryDetected` is `{0} (detected)` and wraps whichever value was found.

## New public members

All six are in the plain `net10.0` assembly, so what a closed section says is testable without a
window:

- `MqttPanelText.SummariseBroker(MqttEndpointRequest, MqttEndpointMemory?, MqttConnectionState)`
- `MqttPanelText.SummarisePublish(MqttPublishTally)`
- `MqttStatusText.SummariseBroker(…)` and `MqttStatusText.SummarisePublish(…)`, the static facade
- `MqttPublishRows.Tally(PublishGroupSet)`, which reduces a group set to two numbers from one
  snapshot, so both describe the same moment
- `MqttPublishTally`, a `readonly record struct` of `SwitchedOn` and `Declared`

Both summaries compose through the same seam the Status rows use. The panel assembles no sentence of
its own.

## The module's `.resw` is now held to its built-in text by test

The panel's resource file duplicates `MqttStrings.Builtin` in the form a WinUI host loads, and the
resource file outranks the built-in text wherever it answers. **A string reworded in one and left
standing in the other therefore ships the stale wording**, with every test passing. Three tests now
compare the two as data: the same keys, the same text, and `xml:space="preserve"` on every entry.

## Pre-1.0 — what this minor means for a pin

While the major version stays `0`, a **minor** bump may break the API and a **patch** never does.
This one adds public members and removes none, so an application that renders the panel and reads
its status through the existing members recompiles unchanged and behaves the same. What moves is the
panel's visible copy and three string keys. A consumer that neither translates the panel nor embeds
screenshots of it can raise the pin without further work.

**Raising the pin is not by itself enough for a consumer that builds locally.** The project reference
resolves through `ZeroZeroSharedDir`, which defaults to the sibling working tree; nothing reads the
pinned-ref file to decide which sources compile. Check the sibling clone out at `v0.4.0` — the pin
file records the intent, the working tree decides the build.

## How to consume it

There is no NuGet feed: neither `ZeroZero.Brand.WinUI` nor `ZeroZero.Mqtt.WinUI` can be packed, so
this release is the tag and these notes — which is all a `ProjectReference` on a pinned checkout
needs. Pin `v0.4.0` as the `ref` of the consumer's second `actions/checkout`, or as
`--branch v0.4.0` on a sibling clone.
[Pin a tag](https://github.com/0z00z0/0z0-shared/blob/v0.4.0/README.md#3-pin-a-tag) in the README
carries both shapes, the MSBuild property that lets CI redirect the reference, and the item-glob
exclusions a workspace-subfolder checkout needs.

What a closed section shows in full is
[What a closed section says about itself](https://github.com/0z00z0/0z0-shared/blob/v0.4.0/docs/zerozero-mqtt.md#what-a-closed-section-says-about-itself)
in the wiring guide, immediately before
[The info-text ownership split](https://github.com/0z00z0/0z0-shared/blob/v0.4.0/docs/zerozero-mqtt.md#the-info-text-ownership-split),
which is what decides whether a string is the module's to write at all.
