A test release. **No API change and no behaviour change** — every public signature, every payload
and every wire decision is `v0.3.0`'s. What it carries is coverage of the one part of the connection
that never runs during development: what happens after the network drops.

## What was untested

`MqttConnection` has reconnected on an escalating backoff since `v0.1.0` — a floor that doubles to a
cap, a session proven stable resetting it, and a session that dies inside the flap window escalating
it instead of resetting — and none of it was asserted anywhere. The failure mode this leaves open is
particular to reconnect code: it is inert until a broker goes away, so a green build, a working
application and a passing suite all say nothing about it, and the first observation of a mistake is
in the field. The two shapes it can take are a tight retry loop hammering a broker, and a healthy
connection sitting on a minute-long wait because one blip pushed the delay to the cap and nothing
brought it back down.

## What is asserted now

Twelve tests in `MqttReconnectBackoffTests`, driving whole sequences rather than reading constants
back:

- **The ladder from the first failure.** Each failed round waits twice the last, and the doubling
  stops at the cap rather than passing it.
- **The stability reset.** A connection that outlives the flap window returns to the floor, so one
  blip does not leave a healthy link reconnecting a minute late for the rest of the session. The
  window's edge is pinned in both directions.
- **Flap escalation.** A peer that accepts the connection and drops it again inside the window
  escalates on every flap. A flapping broker cannot pull the retry rate back to continuous by having
  each connect read as a success.
- **A resume from standby is not a flap.** The suspend killed the socket, so the session that ended
  with it is forgotten and the delay returns to the floor.
- **The wake guard.** MQTTnet raises its disconnect event for a connect that never succeeded as
  well, with the "was connected" flag clear; only a lost session may cut a wait short.
- **Cancellation.** A shutdown arriving mid-wait ends the wait, a wait asked for after the shutdown
  never starts, and a wake is spent once it has fired rather than leaving every later wait to return
  at once.

Each of the six rules — floor, cap, doubling, flap window, stability reset, flap escalation — plus
the wake guard and the cancellation path was broken in turn and confirmed to fail a test that names
it. The suite spends under a second on the whole file: the decision is driven directly and handed
the instant, so a sequence spanning minutes of broker time is asserted in microseconds.

## The neighbouring failure paths

Five tests in `MqttConnectionRecoveryTests`, against the fake broker on a loopback listener, cover
what the maintain loop does when the connect path fails rather than succeeds:

- **A throw on the connect path drops the socket.** A session left half-built reads as connected, so
  the loop takes neither branch on the next pass and the device is alive on the broker with no
  announcement, no availability and no command subscription until the process restarts.
- **A status subscriber that throws does not cost the connection.** `StateChanged` runs inside the
  connect sequence, so an unguarded throw from a host's status line would be read as a connect
  failure and drop the socket on every pass.
- **A resume from standby bounces the socket and announces online again**, rather than leaving the
  entities at the Last Will while the machine is awake.
- **A round where nothing answered is retrying, not failed.** The two drive the same status line and
  send a user to different fields.
- **Removal over a link that is not there removes nothing, and says so.**

Each was mutation-checked the same way.

## The one code change

`MqttReconnectBackoff` is new and **internal**: it holds the reconnect delay and the session it is
judged against, which the maintain loop previously kept in two locals. The policy — the floor, the
cap, the arithmetic and the flap window — stays on `MqttConnection` and is unchanged. `DelayOrWake`
and `Wake` widen from `private` to `internal` so the wait can be driven without waiting one out.

Nothing here reaches a consumer: the type is internal, both widened members are internal, and the
maintain loop makes the same decisions in the same order it always did.

## Pre-1.0 — what this patch means for a pin

While the major version stays `0`, a **minor** bump may break the API and a **patch** never does.
This one adds no public member and removes none, so raising a pin from `v0.3.0` to `v0.3.1` cannot
change what an application does.

## Everything else

Unchanged from `v0.3.0`: the seven source projects and their one-way dependency, every public
signature, the entity model, the device document, identity, the ledger's shape on disk, the
encryption model, the endpoint sweep and every behaviour of the panel. `v0.3.0`'s notes remain the
account of what that release changed, and `v0.1.0`'s **Differences from an earlier shape** tables
remain the migration reference.

## Requirements

.NET 10 SDK. Windows 10 1809 (build 10.0.17763) or later with the Windows App SDK for the WinUI
assemblies; `ZeroZero.Brand.Core`, `ZeroZero.Config`, `ZeroZero.Mqtt` and `ZeroZero.Mqtt.Discovery`
are plain `net10.0` and portable in isolation. The MQTT module requires an MQTT 5.0 broker and, for
discovery, Home Assistant 2024.11.0 or later.

## How to consume it

There is no NuGet feed: neither `ZeroZero.Brand.WinUI` nor `ZeroZero.Mqtt.WinUI` can be packed, so
this release is the tag and these notes — which is all a `ProjectReference` on a pinned checkout
needs. Pin `v0.3.1` as the `ref` of the consumer's second `actions/checkout`, or as
`--branch v0.3.1` on a sibling clone.
[Pin a tag](https://github.com/0z00z0/0z0-shared/blob/v0.3.1/README.md#3-pin-a-tag) in the README
carries both shapes, the MSBuild property that lets CI redirect the reference, and the item-glob
exclusions a workspace-subfolder checkout needs.

690 unit tests across `ZeroZero.Brand.Core`, `ZeroZero.Config`, `ZeroZero.Mqtt` and
`ZeroZero.Mqtt.Discovery`, all passing on `windows-latest` in Release. The release is gated on them.
