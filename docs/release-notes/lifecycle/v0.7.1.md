**The lock says which acquisition it made, and the wiring order in the guide is corrected.** One
addition to the surface, no removal, and a wiring order that stops costing a consumer its startup
line.

**Patch.** Nothing is removed or renamed, `TryAcquire` keeps its signature and its answer, and
nothing recompiles. An application that changes no code gets one behaviour difference, described
below.

## The startup line neither consumer could write

`TryAcquire` answered true or false, and the acquisition treated an abandoned mutex exactly as it
treated a free name. So "this is the first instance" and "the instance before this one died without
letting go" arrived as the same answer, and the second is the one worth a line in a log.

`Acquire(name, wait)` answers a `SingleInstanceOutcome` instead:

| Outcome | What happened |
|---|---|
| `TakenFree` | Nobody held the name. |
| `TakenAbandoned` | The previous holder died without releasing; the wait granted ownership anyway. |
| `RefusedHeld` | Another instance still held it when the wait ran out. |
| `RefusedDenied` | The name exists under rights this process does not have. |

`outcome.IsTaken()` is the two taken outcomes and nothing else. `TryAcquire` is unchanged and now
answers `IsTaken()` over the same acquisition, so an application that wants the plain question keeps
asking it. A second call under the same name reports the outcome the first one had.

## An access error is now a refusal, not an exception

This is the one behaviour change. Opening a name held under rights the process does not have — a
second account's instance, or one running elevated — used to throw an access error out of
`TryAcquire`, into a process that has no logger yet and so has nothing to say about it. It is
`RefusedDenied` now: the process does not become the instance, and it is told why.

**Everything else still throws, deliberately.** A name too long, or a semaphore or event already
under that name, is the application's own error. Answered as a refusal it would look like an
ordinary second instance and never be found. And nothing is ever caught into a taken outcome: the
lock cannot fail open into two instances.

## The wiring order in the guide was wrong, and the trap enforcing it was self-inflicted

0.7.0's guide built the lifecycle with a live log sink and armed the exit hook **before** taking the
lock, and a trap insisted on that order. It forces the whole of the logging setup above the lock,
which is why the acquisition happens where there is nothing to log with.

**The lock never needed it.** `SingleInstanceLock` is static and takes no log sink, `ProductDataPath`
depends on nothing, and `Relaunch.WasRelaunched(args)` gives the wait its one argument without
anything being constructed. So the order is: the data folder, the relaunch check, the acquisition,
return on a refusal — and only then the log, the lifecycle and `Arm()`.

Arming after a successful acquisition removes two traps at once. The refusal path arms nothing, so
it starts nothing, so **it no longer has to mark itself deliberate**; and there is no arm-before-the-
lock rule left to state, because the hazard it warned about was created by the arming it required.

**What that order costs, stated rather than hidden.** A clean exit between the process starting and
the lock being taken now reaches no hook and is not relaunched. What exits in that window is the
refusal, which must never relaunch — a relaunched second instance finds the lock held again and goes
round until the limiter stops it. The other ways out are not clean exits: an unusable data folder or
an impossible mutex name throws, and a crash raises no exit event at all, so no amount of arming
early ever covered them. That last one is measured, not assumed: a test arms the hook, kills the
process with an unhandled exception, and reads from outside that nothing was started.

Anything an application puts in front of the lock — a version switch, a command line it refuses —
now exits without being relaunched, which is what it should have done all along.

## What the notes for 0.7.0 say

They carry the old order as one of three traps worth knowing. Released notes are not rewritten; this
page is the correction.

## What the component still does not do

**A crash never reaches the hook**, so relaunch covers the clean exit nobody asked for and nothing
else. An application adopting this retires its own single-instance lock and its own relaunch
limiter, and keeps its crash watchdog. `docs/adopting.md` now says so where the overlap was easiest
to assume.
