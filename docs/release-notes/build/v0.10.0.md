**The family moves to .NET 11 and every pin to its latest stable release.**

**Released** not yet; prepared 2026-11-19

**Minor.** The application block's target framework moves from `net10.0-windows10.0.26100.0` to
`net11.0-windows10.0.26100.0`, and the Windows App SDK under every application moves three releases.
No property, target or guard is added or removed.

## Taking it

- Install the .NET 11 SDK, and raise any `global.json` SDK version and any `setup-dotnet` version to
  11.0.100 or later.
- Raise `ZeroZero.Build` in `global.json` to 0.10.0, or move the sibling checkout to this commit.
- A project that takes the application block gets `net11.0-windows10.0.26100.0` with the import.
  Every other project that names `net10.0` or `net10.0-windows…` itself changes it to `net11.0`.
- A direct reference to a pinned package moves to the new pin in the same change: a reference below
  a pin is `NU1605`, and a test project's `Microsoft.NET.Test.Sdk` or `xunit.runner.visualstudio`
  below the pin fails the restore.
- **The runtime an end user needs moves with the Windows App SDK.** An unpackaged application built
  under this kit needs `Microsoft.WindowsAppRuntime.2` at 2.7.0.0 registered for the user. An
  installer that carries the runtime, a workflow that installs it, and any bootstrap or prerequisite
  check written against 2.4.0 move to 2.7.0 with it. A self-contained publish carries the runtime in
  its own folder and needs nothing registered.
- **The .NET 11 desktop runtime is required on the end user's machine** for a framework-dependent
  application; a self-contained publish carries it.

## What the raise is proved against

The whole solution builds in Release on .NET 11 under these pins with no new warning, and the full
test suite runs under them. The shared windows are not yet signed off on screen at Windows App SDK
2.7.0.
No consuming application is built here, so each application's own windows are looked at on screen
when it takes the kit.
