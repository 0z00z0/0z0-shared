**The Windows App SDK pin moves from 2.2.0 to 2.4.0.** The kit is the only place that number can
move: it switches `VersionOverride` off, so no consuming application can raise the platform package
on its own, and everything two Windows App SDK releases fixed stays out of reach until the pin here
moves.

**Minor.** No MSBuild file changes, no property moves, no guard is added, and nothing in a consuming
project file has to change. It is a minor because the platform under every application in the family
moves two releases at once, and the Windows App Runtime an end user must have registered moves with
it.

## What the raise gives

From 2.3.1:

- `XamlOptionalChanges`, which opts a build into XAML breaking changes one change id at a time
  rather than all at once.
- A set of XAML startup, styling and resource-lookup optimisations, several of them opt-in through
  the `DefaultStyleOptimizations` and `OptimizeApplyStyles` change ids: lighter `FontIcon` and
  `BitmapIcon` visual trees, and faster `ThemeResource` and `ResourceDictionary` lookup.
- A crash fix in `UniformGridLayout` and `FlowLayout` when a collection change reaches an
  `ItemsRepeater` that is no longer loaded.
- A structured-JSON language-model call, and ARM64EC support for Windows ML.

From 2.4.0:

- Touchpad and mouse haptics through `Windows.Devices.Haptics`, and single-finger touchpad panning,
  where the hardware supports them.
- A fix for the storage pickers leaving the calling window without keyboard focus once the file
  dialogue closes.
- A fix for a touch or pen contact crashing on leaving a scrollable area, and for a composition
  engine crash in `VisualInteractionSource.TryRedirectForManipulation`.
- A fix for environment-variable inheritance breaking MRT Core in a child process, and for
  `MrmGetFilePathFromName` returning the wrong error code where no PRI file is present.

## Taking it

Take the kit at 0.9.0 and rebuild. Nothing in the project file changes: the pin is central, the
`PackageReference` carries no version, and the raise arrives with the import.

**The runtime an end user needs moves with it.** The 2.x framework package carries the SDK's own
number, so an application built against this kit needs `Microsoft.WindowsAppRuntime.2` at 2.4.0.0
registered for the user rather than 2.2.0.0. An installer that carries the runtime, and any
bootstrap or prerequisite check written against 2.2.0, moves to 2.4.0 with it. An application that
publishes self-contained carries the runtime in its own folder and needs nothing registered, but
still ships the newer one.

The pin stays a floor. An application that holds its own direct reference may pin higher, and NuGet
unifies the package graph on the version nearest the consuming project.

## What the raise is proved against

Every WinUI assembly in the family — the About window and brand resources, the shared controls, the
MQTT settings panel, the settings window shell and the tray host — compiles against 2.4.0 with no
new warning, and the repository's own interactive rig renders the settings shell in both themes, the
About window in both its hosted shapes, and the tray host's icon and menu at that version.

No consuming application is built here, so the effect on a real application's own windows is not
covered by that. A platform package changes under every application at once, and what it breaks
tends to appear in windows, icons and rendering rather than in a test run.
