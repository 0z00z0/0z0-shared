**Builds stop leaving worker processes behind.** One new file in the package, a response file to
copy to a repository root; no property moved, no guard was added, and nothing recompiles.

**Patch.** Every existing MSBuild file is unchanged, and a repository that ignores the new file
builds exactly as before.

## What a build leaves behind without it

MSBuild keeps its worker nodes alive for fifteen minutes after a build so the next one can reuse
them. A worker node is launched with CREATE_NO_WINDOW, which allocates a console all the same, so
every node also holds a console host process. On a sixteen-core machine one clean build of this
repository's solution ends with fifteen worker nodes and fifteen console hosts still running,
holding about 2 GB; builds started inside the fifteen minutes stack another set whenever the first
set is busy.

Node reuse is on unless a build turns it off, and the .NET CLI does not turn it off. With no
response file on the path, the workers a command-line build starts carry `/nodeReuse:true` on
their own command lines and outlive the build that started them.

The switch `-nodeReuse:false` takes that to nothing: over the same clean build, no worker node and
no console host survives it.

## What it costs

Nothing measurable. Clean builds of the solution measure 285 s and 236 s without the switch and
226 s with it — inside the spread between the two runs without it. Parallelism is untouched: the
build still runs on fifteen worker nodes, and they end with it rather than outliving it.

## Taking it

Copy `templates/Directory.Build.rsp` to the root of the repository, beside `Directory.Build.props`.
MSBuild finds it by walking up from the directory of the project being built, whatever directory
the build was started from, so it covers `dotnet build`, `dotnet test` and `dotnet pack` alike. It
reaches a build that goes through the MSBuild command line.

Nothing is locked. MSBuild reads the response file before the command line, so a switch on the
command line wins over one in the file, in either direction: `-nodeReuse:true` there restores the
old behaviour for that build, and `-nodeReuse:false` there ends the worker nodes of a build in a
repository that has no file.

## Telling whether it works

Node reuse changes whether the worker nodes end with the build, not how many the build uses. The
worker count across a rebuild is the same with the switch and without it, so a count taken while
the build runs shows the switch doing nothing. What shows it is what is still running once the
build has exited.

A count of newly started processes gives the same false negative, because a build with node reuse
on attaches to idle nodes an earlier build left behind and starts none of its own. Read
`-nodeReuse:` off each worker's own command line rather than inferring it from a count.

## Why it is not a property

Node reuse is settled when MSBuild starts, before a project file is evaluated, so no property in
`ZeroZero.Build.props` reaches it: `-p:MSBuildDisableNodeReuse=true` leaves all fifteen nodes
running. A response file is the only shape this setting has.

Two neighbouring candidates are deliberately absent, each for a measured reason. Turning the shared
compiler server off through `UseSharedCompilation` leaves the residue identical, at fifteen nodes
and fifteen console hosts, and adds build time. A worker cap through `-m` does lower the peak, but
the .NET CLI passes its own `-maxcpucount` on the command line, which beats an `-m` written in the
response file, so a cap set there changes nothing.

That override is switch by switch and not file-wide. The CLI passes no node-reuse switch of its
own, so `-nodeReuse:false` in the file is what decides node reuse for a CLI build, while `-m` in
the same file does not decide the worker cap.
