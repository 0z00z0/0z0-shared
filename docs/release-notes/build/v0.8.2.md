**The response-file template says what it does, and one runtime pin moves.** The template is the
file a repository copies to its own root; the copy taken from 0.8.1 carries an account of node reuse
that leads a reader to the wrong conclusion about what the .NET CLI overrides.

**Patch.** No MSBuild file changes, no property moves, no guard is added and nothing recompiles.

## What the earlier template got wrong

The 0.8.1 template said that `dotnet build` appends its own `-maxcpucount` after the response file,
so an `-m` written there is overridden. That is true and it is the wrong lesson to draw from it: read
as a statement about the file, it says the command line beats the response file, and from there
`-nodeReuse:false` in the same file looks equally inert. It is not. The override is switch by switch.
The CLI passes a worker cap of its own and no node-reuse switch at all, so the cap in the file does
nothing while the node-reuse switch beside it decides.

Two smaller corrections travel with it. Node reuse is on unless a build turns it off, and the .NET
CLI does not turn it off — the earlier text left the default unstated, so a reader could take the
switch for a belt-and-braces repetition of what MSBuild already did. And MSBuild walks up from the
directory of the project being built rather than from the directory the build was started in, which
is what makes the file cover a solution build from anywhere in the tree.

The template now also carries the reading that tells whether it is working: what is still running
once a build has exited, never a worker count taken while one runs. A count during the build is
identical either way, and a build with node reuse on attaches to idle nodes an earlier build left
behind and starts none of its own, so a count of newly started processes reads zero as well. Both
look like a switch doing nothing.

## Taking it

Copy `templates/Directory.Build.rsp` over the copy at the repository root. Nothing else in the
package has moved, and a repository that has not copied the file builds as before.

## Also in this release

`Microsoft.Win32.SystemEvents` moves from 10.0.11 to 10.0.12, which is the current .NET 10 servicing
release. The package is the runtime's own assembly republished under the runtime's number, with one
API across the train, and the pin's rule is that it tracks that number rather than whatever a package
cache happens to hold.

It is a floor. A consuming application that holds no direct reference — which is both of them, since
the assembly arrives only through `ZeroZero.Lifecycle` and `ZeroZero.Tray.WinUI` and no type of it
reaches a public signature — resolves 10.0.12 and needs no change. One that does hold a direct
reference below 10.0.12 meets NU1605 and raises its own to match.
