A documentation release carrying one new test and no code change. **No API change** — no public
signature is added, removed or altered, and no behaviour differs from `v0.3.3`. It exists because
what it states has a data-loss path behind it: **one unrecognised enum name in the settings file
costs the whole document, and the copy left aside is the only thing that survives.** A consumer that
pins tags reads the guides at the tag it pinned, so a correction left on `main` never reaches it;
`v0.2.1` and `v0.3.3` were cut for the same reason.

It also carries the corrected `v0.3.3` record in-tree. The released `v0.3.3` notes omit the settings
carry-across obligation that release exists to state, and a tag cannot be rewritten.

## One unknown enum name costs the whole settings file, not the field it sits in

`MqttSettings` is read as a single deserialisation. **A value no enum member answers to fails that
deserialisation**, so the broker host, the port, the credentials, the device id and the group
switches all revert to their declared defaults alongside the field that carried the bad name. Three
settings are enum-typed and carry the risk: `TransportMode`, `EncryptionMode` and
`CertificateTrust`.

**The visible symptom is a blank broker host and an inert connection** — `Enabled` reads false,
publishing does nothing, and every entity the installation had goes unavailable. That is
indistinguishable from a missing file, so the failure reads as a fresh installation rather than as a
document that was discarded.

An unknown *property* behaves differently and is the reason this surprises: a name the shape does
not declare is ignored, the rest of the document reads, and nothing is quarantined. The blast radius
of an unknown **value** is the file; the blast radius of an unknown **key** is nothing.

### The original is copied aside and then immediately overwritten

The file is copied to `mqtt.<timestamp>.bad.json` beside the settings file, and the defaults are
written over the original **as the store is constructed** — not on the next `Update`, and not on the
next application start. **That copy is therefore the only surviving record of what the user had**,
and only the three most recent copies are kept, so a repeated failure on successive starts ages the
earliest one out.

### Removing or renaming an enum member is a breaking change

It breaks **every installation whose file names the retired member**, and what it costs is the
document rather than that member's own setting. Widen an enum rather than narrow it, and keep a
retired name readable even where it no longer selects anything. A number left on disk by an older
writer still reads, but the module writes member names, so it is a name that has to keep resolving.
Names read case-insensitively, so case alone is not the hazard.

### A carry-across that writes an undeclared name destroys the document it just wrote

The same trap catches the settings migration `v0.3.3` describes. A host moving an existing broker
block into `mqtt.json` writes the document, and the next read discards it whole if any value it
wrote is a name the target enum does not declare — leaving the user with defaults, a `.bad.json`
copy, and no indication that a migration ran at all. Map to member names that exist in the version
being adopted, and remember that a two-state TLS switch is not a three-valued `EncryptionMode`.

### A host can tell its user, and nothing tells the user by default

**Nothing surfaces the quarantine.** The path is readable as
`MqttSettingsFile.File.LastQuarantinePath`, null when nothing has been quarantined, so a host that
wants the user told that a document was set aside reads it once after opening the store and before
anything else reads the settings. Whether the module should say so itself is a design question this
release does not answer; it changes no behaviour.

## The `v0.3.3` notes are corrected in-tree

The released `v0.3.3` notes describe the theming statement and the device-id dialogue change, but
**omit the settings carry-across obligation** — the consequential half of that release. The in-tree
copy now states it: the module reads its own `mqtt.json` and nothing else, so a consumer adopting it
for an installation that already stores broker settings must move them into that file itself;
nothing in the module does it and nothing detects that it was not done. A missing file is
indistinguishable from a fresh installation, so the failure is silent, and a fresh install does not
reveal it. The move belongs in the host, immediately after the store is opened and before anything
reads it, gated on the absence of the module's own file, carried per key rather than per file, with
an absent key never read as `false` or as zero.

The tag `v0.3.3` cannot carry this. A consumer pinned there reads the corrected account at `v0.3.4`.

## The README's account of quarantine is corrected

The README described an unreadable file as "moved aside rather than overwritten", which states that
there is no data-loss path. **Both things happen**: the file is copied aside *and* the original is
overwritten with defaults, in the same construction. The bullet now says so, names the copy's shape
and its retention, and points at `LastQuarantinePath`.

## Pre-1.0 — what this patch means for a pin

While the major version stays `0`, a **minor** bump may break the API and a **patch** never does.
This one adds no public member, removes none and changes no code, so raising a pin from any `v0.3.x`
to `v0.3.4` cannot change what an application compiles or what it does at run time. The files that
differ from `v0.3.3` are the interface guide, the README's quarantine bullet and its pinning
examples, the `v0.3.3` notes, one test, the declared version and these notes.

**Raising the pin is not by itself enough for a consumer that builds locally.** The project reference
resolves through `ZeroZeroSharedDir`, which defaults to the sibling working tree; nothing reads the
pinned-ref file to decide which sources compile. Check the sibling clone out at `v0.3.4` — the pin
file records the intent, the working tree decides the build.

## Everything else

Unchanged from `v0.3.3`: the seven source projects and their one-way dependency, every public
signature, the entity model, the device document, identity, the ledger's shape on disk, the
encryption model, the endpoint sweep, the reconnect ladder, the panel's theme keys and every other
behaviour. `v0.3.3`'s notes remain the account of what a host's branding reaches, `v0.3.2`'s remain
the account of the connect storm and the eviction paths, and `v0.1.0`'s **Differences from an
earlier shape** tables remain the migration reference.

## Requirements

.NET 10 SDK. Windows 10 1809 (build 10.0.17763) or later with the Windows App SDK for the WinUI
assemblies; `ZeroZero.Brand.Core`, `ZeroZero.Config`, `ZeroZero.Mqtt` and `ZeroZero.Mqtt.Discovery`
are plain `net10.0` and portable in isolation. The MQTT module requires an MQTT 5.0 broker and, for
discovery, Home Assistant 2024.11.0 or later.

## How to consume it

There is no NuGet feed: neither `ZeroZero.Brand.WinUI` nor `ZeroZero.Mqtt.WinUI` can be packed, so
this release is the tag and these notes — which is all a `ProjectReference` on a pinned checkout
needs. Pin `v0.3.4` as the `ref` of the consumer's second `actions/checkout`, or as
`--branch v0.3.4` on a sibling clone.
[Pin a tag](https://github.com/0z00z0/0z0-shared/blob/v0.3.4/README.md#3-pin-a-tag) in the README
carries both shapes, the MSBuild property that lets CI redirect the reference, and the item-glob
exclusions a workspace-subfolder checkout needs.

The quarantine statement in full is
[Retiring an enum member breaks every file that already names it](https://github.com/0z00z0/0z0-shared/blob/v0.3.4/docs/zerozero-mqtt.md#retiring-an-enum-member-breaks-every-file-that-already-names-it)
in the wiring guide, immediately after
[Carrying an existing broker block across](https://github.com/0z00z0/0z0-shared/blob/v0.3.4/docs/zerozero-mqtt.md#carrying-an-existing-broker-block-across),
which states the settings obligation the corrected `v0.3.3` notes summarise.

## Verified

700 unit tests across `ZeroZero.Brand.Core`, `ZeroZero.Config`, `ZeroZero.Mqtt` and
`ZeroZero.Mqtt.Discovery`, all passing on `windows-latest` in Release. The release is gated on them.
One test is new since `v0.3.3`: it writes a settings file holding an unrelated setting beside an
enum name no member answers to, then asserts that the unrelated setting reverts to its default, that
a quarantine copy exists, and that the copy still holds the value the file was discarded for.
