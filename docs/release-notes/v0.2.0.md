Corrections found by the first application to adopt the MQTT module against `v0.1.0` — a build, a
warning, three gaps a consumer had to work around, two measured against a live broker, and the
guide. One of the guide's statements was wrong in a way that cost that consumer its first build.

## `v0.1.0`'s one-reference guidance was wrong

**`v0.1.0` told a consumer it could take a single `ProjectReference` on `ZeroZero.Mqtt.WinUI` and
have the whole module. It could not.** That project referenced `ZeroZero.Mqtt` and
`ZeroZero.Brand.WinUI` only, so every `ZeroZero.Mqtt.Discovery` type — the entity classes, the
entity set, the publisher and its setup — failed with `CS0234` in a consumer that followed the
document. The dependency table in the guide was right and the prose beside it was wrong.

The fix is in the code, not the document: `ZeroZero.Mqtt.WinUI` now references
`ZeroZero.Mqtt.Discovery`, so the documented contract is true. A consumer that worked around it by
adding a second reference can drop that reference or keep it; both build.

## Pre-1.0 — read this before pinning

While the major version stays `0`, a **minor** bump may break the API and a **patch** never does.
This release adds to the API and breaks none of it; the minor bump is for one change of behaviour a
host can observe. The connect sweep and the device removal also behave differently, but only in ways
a consumer would have asked for — see **Fixed**.

**The API-visible behaviour change:** `MqttSettingsPanel.Reload()` and `MqttSettingsPanel.Revert()` now throw an
`InvalidOperationException` when the panel has not been initialised, where they previously returned
silently. Both read the settings store the panel is handed on `Initialise`, so neither could ever do
anything without it, and a host calling one from a general refresh step ahead of its own wiring got
no effect and no error — surfacing later as a blank panel with nothing to trace it to. A host that
calls either before `Initialise` needs its ordering fixed. `Refresh()` and `Cancel()` are unchanged
and stay silent: neither reads the store.

## What is new

**`MqttEntity.RepublishLastOnConnect`** makes a per-channel capability declarable for the first
time. `MqttChannel.RepublishLastOnConnect` existed and was honoured by the connection, but every
channel composed from an entity carried it false and no declaration could set it. Declared, an
entity whose reading is absent keeps whatever it last published instead of announcing itself absent,
and a (re)connect re-sends that payload. It is for an entity whose producer has a first reading to
wait for, which otherwise shows a visible unknown on every connect before its first real value.
Off by default, and two consequences are stated in the guide: the entity no longer clears when its
reading goes away, on any pass rather than only on connect, and one that has never had a reading
publishes nothing at all.

**`RetiredChannel`** evicts a retained value topic that no entity claims. `RetiredEntity` reaches a
single-component discovery config; nothing reached the payload topics an earlier implementation left
behind — a JSON-per-device design's shared payload topic, or a state topic under a key no entity
carries any more. A consumer had no declaration for those at all and had to hand-roll a persisted
one-shot flag. `RetiredChannel` names a channel key under `<topicRoot>/<deviceId>/`, the topic is
emptied once per identity and the composed topic is written into the ledger, exactly as a retirement
is. Declared through `DiscoveryPublisherSetup.RetiredChannels`. A key naming a live entity that has
state is refused at declaration, as is a key that could not be published as a channel.

**`MqttPanelFontFamily`** is a sixth theme key, and the panel's only supported route to a host's
typeface. The five existing keys are all `SolidColorBrush`, and because every element the panel
styles carries an explicit style, a host's *implicit* `TextBlock` style never applies — so a studio
wanting its own face had no route at all. One key covers the panel: the styles that render text set
it, and the panel root sets it so the rows built in code inherit it. A toolkit `SettingsCard`'s own
header keeps the stock face, because the toolkit's style carries the family; everything else on the
panel follows the key. It defaults to the stock WinUI face, so a host that declares nothing sees no
change.

## Fixed

**A fresh install against a proxy-fronted broker no longer waits minutes before publishing.**
Measured: first connect over a public route took **3 minutes 9 seconds**, because a CDN in front of
the broker **drops SYN** on the MQTT TCP ports rather than refusing them — so the sweep sat in
`SYN_SENT` through 1883 and 8883, spending the whole connect budget on each, before reaching the
WebSocket candidate on 443 that worked.

A refusal and a black hole are distinguishable and no longer cost the same. Every candidate now
opens a socket first, under a 3-second budget that applies **only** to a candidate that has produced
no response whatsoever; anything that answered and then failed keeps the full budget, because a
candidate that answered is one worth waiting on. A round in which nothing answered escalates the
next round to the full budget for the socket stage too, so a genuinely slow broker on a poor link
connects on the second round rather than never, and a sweep of one pinned candidate always gets the
full budget. Measured against a black-holed address: **83.4 s before, 12.3 s after**. Nothing was
made concurrent and no transports are raced — no credential reaches more endpoints at once than
before. `MqttProbe.SilentTimeout` is the constant, and the Test-connection path uses the same rule so
the two cannot disagree about whether a fronted broker is reachable.

**Removing a device no longer writes the module's own noise into the host's log.**
`RemoveDeviceAsync` emptied the command topics while still subscribed to its own command wildcard, so
the process received its own zero-length payloads back and refused each one — measured at **46**
`COMMAND REFUSED … (Malformed)` lines across two passes, in the consuming application's log, at
exactly the moment something notable was happening. The connection now unsubscribes from the command
filter before the removal clears those topics, which stops the echoes at the broker rather than
filtering them after arrival and opens no window: a removal ends in a disconnect. A zero-length
command arriving outside a removal is still reported exactly as before — that is how a retained
command gets cleared.

**A moved topic root no longer strands its availability topics.** Abandonment is keyed on the device
id, so a topic root that moved under an unchanged device id was the one case it did not cover: the
old availability topic kept its retained payload for ever, asserting that a device which had gone was
online, and no declaration reached it. Both availability topics are now emptied in the sweep when the
composed address differs from the recorded one.

**`PRI257` no longer lands in every consumer's build.** `ZeroZero.Mqtt.WinUI` ships
`Strings\en-GB\Resources.resw` with no default-language resources, which warned in the build of
anything referencing it, for ever. The project now declares `DefaultLanguage` as `en-GB`. A
consuming **app** that ships language-folder resources of its own still declares the property in its
own project — a merged app PRI is built from the app's resources and no library can declare the
default on its behalf. Both guides say so.

## The interface guide

[`docs/zerozero-mqtt.md`](https://github.com/0z00z0/0z0-shared/blob/v0.2.0/docs/zerozero-mqtt.md)
gains the material the first adoption had to work out for itself.

**Declaring the migration** is now stated as what it is. For a consumer with an installed base,
declaring every current entity as a `MigratingEntity` **is** the migration — nothing else carries an
existing entity across, and an entity left undeclared is announced as a new one while its old
single-component config stays retained beside it. The guide had documented `MigratingEntity` as an
exotic case, apart from **Differences from an earlier shape**, and step 5's wiring example showed
`Retired` while omitting `Migrating` entirely. The two are now one section, and the wiring example
shows all three declarations.

It also states the consequence a reader would otherwise work around: on a **fresh** install every
migration declaration fires against a topic that never existed, the whole set is ledgered on the
first connect, and it never repeats. That is the accepted cost of one declaration serving both
populations, and there is no first-run gate worth writing.

**The first migration against a real installation** is a new section. That announcement happens
once and has no undo; every run after it reads the ledger and does nothing. Take a receiver backup
before it — a deleted entity's record, including its registry id, is kept and serialised, so a
backup makes the operation reversible. The guide is also explicit about what a passing validation
covers: exercising the module against a test device establishes that it connects, publishes, accepts
commands and evicts correctly, and establishes nothing about one installation's accumulated
customisations — renames, area moves, hidden or disabled entities, hand-chosen entity ids.

**Whether the old availability topic needs anything is now stated as the conditional it is.** A
consumer that keeps its topic root and device id declares only the value topics its predecessor
published: the availability topic is composed identically and taken over rather than orphaned, which
is also why the Last Will keeps working across the upgrade. A consumer renaming either is in the
other case, and the guidance is to migrate first and rename afterwards, because the record left by
the first connect is what clears the old topics.

**Overriding a theme key safely** is a new subsection. An override is supplied in every theme the
host supports; a key defined once and reused across themes is the one that goes invisible, and it
fails silently with a green build. The guide says to check both themes on screen and to measure
rather than look — sample the darkest glyph pixel against its ground and compute the contrast ratio,
where below about 4.5:1 fails and this particular failure reads close to 1:1. The module's own
defaults measure 6.17:1 in light and 9.09:1 in dark.

**Constructing `MqttSettingsFile` does not create the file.** The constructor reads the file if it
is there and takes the declared defaults if it is not; nothing is written until an `Update` changes
something or `Save()` is called. That is exactly the fact a host needs to build a has-this-migrated
gate from `FilePath`, and it previously had to be read out of the source. The same holds for
`DiscoveryLedgerFile`.

The four code changes above are documented alongside, and `README.md` and
`consume-mqtt-settings-panel.md` are corrected where they restated the reference set, the theme-key
count or the panel lifecycle.

## Everything else

Unchanged from `v0.1.0`: the four MQTT assemblies and their one-way dependency, the two brand
assemblies, the entity model's seven component types, the device document, identity, the ledger's
shape on disk, the encryption model and the endpoint sweep. `v0.1.0`'s
**Differences from an earlier shape** tables are unchanged and remain the migration reference for a
consumer coming from a per-component, shared-payload implementation.

## Requirements

.NET 10 SDK. Windows 10 1809 (build 10.0.17763) or later with the Windows App SDK for the WinUI
assemblies; `ZeroZero.Brand.Core`, `ZeroZero.Config`, `ZeroZero.Mqtt` and `ZeroZero.Mqtt.Discovery`
are plain `net10.0` and portable in isolation. The MQTT module requires an MQTT 5.0 broker and, for
discovery, Home Assistant 2024.11.0 or later.

## How to consume it

There is no NuGet feed: `ZeroZero.Brand.WinUI` cannot be packed, so this release is the tag and
these notes — which is all a `ProjectReference` on a pinned checkout needs. Pin `v0.2.0` as the
`ref` of the consumer's second `actions/checkout`, or as `--branch v0.2.0` on a sibling clone.
[Pin a tag](https://github.com/0z00z0/0z0-shared/blob/v0.2.0/README.md#3-pin-a-tag) in the README
carries both shapes, the MSBuild property that lets CI redirect the reference, and the item-glob
exclusions a workspace-subfolder checkout needs.

670 unit tests across `ZeroZero.Brand.Core`, `ZeroZero.Config`, `ZeroZero.Mqtt` and
