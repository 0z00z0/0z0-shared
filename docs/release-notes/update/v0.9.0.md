**A self-signed release can now be trusted on the publisher name alone, where the application asks
for it.** With that, a silent trigger that shows nothing for any outcome, a check that is shared
rather than refused when a second caller arrives, an update that starts from a release already
found, release-notes text the host can supply, and refusal wording that no longer claims the file
was deleted.

**Released** 2026-09-20

**Minor.** `UpdateFlow.RunAsync` returns `UpdateFlowRun` rather than `UpdateFlowResult`, and a
second caller arriving during a check is no longer answered `AlreadyRunning`. Everything else is
added: `UpdateTrigger` and `UpdateFlowResult` gain one appended member each, `ExpectedSigner` and
`NativeUpdatePrompts` each gain one optional constructor argument, and `UpdateFlow` gains one
method.

## Trusting the publisher name alone

A self-signed certificate reads as an untrusted root on every machine it has not been installed on,
and until now the only way past that was a thumbprint listed in the application. Pinning closes the
look-alike hole and breaks every certificate renewal, so an application that cannot carry the pin
could not check a release at all.

`new ExpectedSigner(subject, acceptSelfSignedSubject: true)` accepts an intact signature by the
expected subject under an untrusted chain, with no pin. It is off unless asked for: an application
that does not pass it keeps the pin requirement exactly as it was.

- The subject is compared first, whole, without case and with both sides trimmed, so another
  publisher's self-signed certificate never reaches the tolerance.
- Only an untrusted root is tolerated. A file altered after signing, a file with no signature, an
  expired certificate and a chain that cannot be built all still refuse, whatever this setting says.
- The hash the release publishes is still checked first, and still before anything else.
- What it knowingly accepts is a certificate minted with the same name. An application that can
  carry a pin should carry one.

The subject comparison is now case-insensitive for every caller, not only this mode. A pin still
gates the untrusted case without it, so nothing that was refused before is accepted now except
through the new setting.

## A trigger that shows nothing

`UpdateTrigger.Silent` shows nothing for any outcome, a release included. The run carries the
result and the release, and the caller drives its own button:

```csharp
UpdateFlowRun run = await flow.RunAsync(UpdateTrigger.Silent);
if (run.Result == UpdateFlowResult.UpdateAvailable) ShowTheButton(run.Release!);
```

`Manual` and `Scheduled` are unchanged: a manual run reports every outcome, a scheduled one speaks
only when there is something to install.

## A check that is joined rather than refused

A caller arriving while a check is in flight is handed that same check and reads its result — the
same object, not a second request and not a refusal. The shared slot is cleared as the check ends,
before any caller resumes, so a request arriving after that starts a fresh check rather than
reading an answer that has already been given. `AlreadyRunning` now answers a second concurrent
install and never a second check.

## Installing a release already found

`InstallAsync(release)` asks, downloads, verifies, launches and hands over, for a release a check
has already found. Nothing is checked again.

## Refusal wording

No message claims the file was deleted, in any casing. Removing a refused file is attempted after
the decision and its failures are logged rather than shown, so the old sentence could be false in
front of a person. Each reason now has a plain sentence of its own — eleven of them, one per
verification verdict and one per outcome that stops an install — and every one ends the same way:
the file was not run, and updating should happen from the release page instead.

## Release notes in the dialog

`new NativeUpdatePrompts(owner, name, topmost, releaseNotes: release => text)` supplies the text
behind the install dialog's expander. A null function, or a null return, falls back to the release
body with its markdown stripped, as before; an empty return leaves the expander out.

## What a consumer has to change

- `RunAsync` returns `UpdateFlowRun`. A call that compared the returned value with
  `UpdateFlowResult` reads `run.Result` instead. This is a compile error, not a silent change.
- Code that treated `AlreadyRunning` as the answer to a concurrent check gets a real check result
  instead, and can drop the special case.

Nothing else moves. An application that passes neither new argument and reads `run.Result` behaves
exactly as it did on 0.8.0.

## Verifying it

Proved by having been run once rather than by tests of its own: the mode accepting the expected
publisher under an untrusted root and refusing another publisher, the name match ignoring case and
padding and never matching a shorter name, a file altered after signing and an unsigned file still
refusing with the mode on, an installer held open so its removal fails surviving with no message
claiming otherwise, eleven distinct refusal sentences none of which mentions deletion, two callers
reading one check, the silent trigger showing nothing when a release is found, and an update
starting from a release already found.

One case is not proved: a chain fault other than an untrusted chain. Windows will not apply a
signature with an expired certificate, so producing a file signed by one would mean putting a
certificate in a store.

## Unchanged

The download, the published-hash rule, both verification steps, the launch policy, the
stale-download sweep, the scheduler, and every outcome a check can report.
