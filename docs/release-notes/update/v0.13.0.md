**The unattended policy now asks before it downloads, keeps checking while it holds a release, and
can join the check an application's own windows share.** An application may refuse the download of
a release before a byte of it is fetched; a release held back — downloaded or not — no longer stops
the policy finding a newer one; and one check object handed to every flow, the policy's included,
makes simultaneous checks from any of them one request with one answer.

**Released** 2026-09-28

**Minor.** One behaviour changes for an application that sets nothing new: while a release is held,
the policy goes on checking on its cadence, and a strictly newer release takes the held one's place.
Everything else is new and optional, and nothing is removed or renamed.

## Asking before the download

`UnattendedUpdateOptions.MayDownloadNow` is called once a release has been found and before anything
of it is downloaded, with the release, and answers an `InstallMoment` exactly as `MayInstallNow`
does. A refusal keeps the release without downloading it, the tick reports the new outcome
`UnattendedOutcome.DownloadRefused` with the reason and the release, and the next tick asks again.
The refusal is logged once per reason, as a refused launch already is, and the two gates keep their
reasons apart so both refusing on one tick still writes one line each. Null accepts every moment, so
everything found is downloaded as before.

`MayInstallNow` is unchanged: it is still asked immediately before the installer starts, once the
download has verified and the machine-free rule has passed.

An application that keeps installing switched off for the life of the process answers
`MayDownloadNow` with a refusal every time, and the policy then checks on its cadence and reports what
it found without ever downloading it.

## Checking while something is held

A check now runs on its cadence whatever is held: a release found and not yet downloaded, or a
verified installer waiting for the machine to be free or for `MayInstallNow`.

- **A strictly newer release takes the held one's place.** Where nothing of the held release was
  downloaded, it is forgotten at once and the newer one goes through the gates from the start.
- **A verified installer stays until its replacement has verified.** The newer release is asked
  about with `MayDownloadNow`, downloaded and verified; only then is the old installer removed and
  the new one held. Until then the old one is still offered and may still start.
- **A check that fails keeps what is held**, and the tick carries on with it. A newer release that
  does not download or does not verify is forgotten, and the installer already held stays.
- **The same version, or an older one, changes nothing.** Only a strictly newer release replaces
  what is held.

`CheckFailed`, `NothingToInstall`, `NotDue` and `NotPrepared` are now reported only where nothing is
held; with something held, the tick goes on to it and reports where that ended. `CheckCadence.Once`
still checks once: a held release then waits for the gates, never for another check.

`IUpdateService.Discard` removes a prepared installer that will not run, and `UpdateService` takes
the directory it was downloaded into — only where that is a directory of its own making, its prefix
and a fresh identifier under the temporary folder. The member has a default that does nothing, so an
`IUpdateService` written outside the component compiles unchanged and leaves its files to its own
housekeeping.

## One check for every flow

`SharedUpdateCheck` is the joining that `UpdateFlow` already did for its own runs, taken out so more
than one flow can hold it. An application constructs one over its service and hands it to each flow
through `UpdateFlowOptions.SharedCheck`, and to the policy through
`UnattendedUpdateOptions.SharedCheck`. A run arriving on any of them while a check is in flight on
any other joins that check and reads its result.

Only the check is shared. What a run does with the answer is decided by its own trigger and its own
flow's prompts, so the policy's silent run shows nothing beside a manual run in the update window,
and a manual run that joined the policy's check still reports in its window. A shared check built
over another service than the flow's is refused when the flow is constructed.

Null, on either option, gives a flow a check of its own, joined only by its own runs — exactly the
behaviour before this release.

## What has a test

Five guards, each broken once and seen to fail: a refused download downloads nothing and logs once;
a held release still checks on its cadence and finds a newer one; a held installer survives a failed
check and a newer release that does not verify, and is replaced and removed by one that does; two
flows with different prompts read one check and each speaks as its own trigger says, with the
policy's check joining the same way; and `UpdateService.Discard` removes its own download directory
and leaves a directory of the right name elsewhere, or one in the right place under another name.

## Nothing to change

An application that sets none of the three options keeps its wiring. It gains the continued checking
above, and nothing else.
