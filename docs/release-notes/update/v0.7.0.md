**The first release of the update component.** A GitHub-release updater for a desktop application, in
two halves. `ZeroZero.Update` is the flow with no dialogs: find the latest release, compare it with
the running version, download the installer into a fresh private directory, verify it twice, launch
it, sweep stale downloads and schedule the next check. `ZeroZero.Update.Win32` is the entry point —
the dialogs, worded here, and the check-ask-download-verify-launch orchestration that hands over to
the application's own shutdown.

## The two checks, neither optional

**The download is proved whole and proved to be the publisher's.** The SHA-256 is checked against the
hash the release body publishes, and the Authenticode signature is checked against the expected
signer. **Both run twice** — once after the download and again immediately before launch.

Under an untrusted certificate chain the certificate must also be one the application pins by
thumbprint. A subject-only rule would accept any self-signed certificate spelling the same name, which
is no check at all.

**Pin the next certificate one release ahead.** A certificate rotated in with the release that first
expects it is refused by every version already installed — which is every version that matters.

## What is in the package

- **`UpdateService`** — check, prepare, launch, sweep. Each answers with a named outcome rather than a
  boolean: up to date, nothing released, rate limited, unreachable, an invalid response, an installer
  asset that is not there, a hash that is not published, a hash that is ambiguous, a download that
  failed, or a file that was refused.
- **`InstallerVerifier`** and **`ExpectedSigner`** — the hash and the signature, and what counts as a
  match.
- **`UpdateScheduler`** — the first check after a settling delay, then one a day. **Nothing is
  persisted**, so the interval counts from when the process started.
- **`UpdateFlow`** and **`NativeUpdatePrompts`** — the task dialog offering install, release notes or
  later, the message boxes for everything that can go wrong, and the flow that ties them to the
  service. Its result names all nine ways it can end.

## Four things a consumer must get right

**Exactly one 64-digit hexadecimal token in the release body.** None means the hash is not published;
two means it is ambiguous. Both download nothing.

**The installer asset's name must match exactly, case included.**

**The release tag must be a plain version.**

**The running version is the entry assembly's.** A host whose entry assembly is not the product sets
it explicitly.

Anonymous GitHub requests are limited to 60 an hour per address. A rate limit is reported as a state,
not as a failure.

## Deliberately not here

The installer itself — this component assumes a per-user installer needing no elevation. The shutdown
behaviour: the flow calls the application's callback once the installer process exists, and what
happens then is the application's. And the release workflow that signs the installer, attaches it and
writes the hash into the body.

## What it depends on

`ZeroZero.Update` takes `ZeroZero.Primitives`; `ZeroZero.Update.Win32` takes that and
`ZeroZero.Win32`. No third-party package in either. **Both target plain `net10.0`, the Win32 half
included** — its dialog is a native task dialog taking a window handle and touching no XAML, so it is
a Win32 dependency rather than a WinUI one.

## Why 0.7.0 and not 0.1.0

Every component in the family starts at 0.7.0. Up to and including 0.6.0 one number released every
package together; 0.7.0 and above means a component releases on its own.
