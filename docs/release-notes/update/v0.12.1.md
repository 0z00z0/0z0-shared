**A consuming application can now choose a check that runs once and never again, instead of a
periodic interval.** `UnattendedUpdateOptions.Cadence` takes `CheckCadence.Once`, which checks a
single time after `InitialDelay` and stops checking for the rest of the process, whatever that
check finds — something no interval value can express, since even the longest one checks again
eventually.

**Released** 2026-09-28

**Patch.** `CheckCadence` is a new type and `Cadence` is a new property with a default
(`CheckCadence.Periodic`) that behaves exactly as `CheckInterval` already did. No existing type is
given a new member, nothing is removed or renamed, and no member changes signature, so a consumer
that changes no code keeps exactly its current behaviour.

## What a consumer on 0.12.0 gets

`UnattendedUpdateOptions.CheckInterval` only expresses a periodic cadence: at any value, it checks
again eventually. An application that wants one check shortly after starting and none for the rest
of the run had nothing to set for that — the smallest interval still checks a second time once it
elapses.

## What it does now

`Cadence` chooses between two policies:

| `CheckCadence` | What runs |
|---|---|
| `Periodic` | A check runs once `CheckInterval` has passed since the last one. The default; unchanged. |
| `Once` | A check runs once, after `InitialDelay`, and never again for the life of the process — a check that fails counts the same as one that succeeds. |

The cadence governs checking only. An installer already found and prepared keeps following the
machine-free rule, `MayInstallNow` and the retry when it could not start, whichever cadence found
it: the scheduler keeps ticking at `RetryInterval` and those rules keep applying, and a tick under
`Once` after its one check simply finds no further check due.

## Verifying it

One test drives `CheckCadence.Once` through a check that fails: the first tick checks and reports
`CheckFailed`, and a second tick reports `NotDue` and starts no second check. Breaking the line that
spends the single check on a failed attempt turns that second tick back into `CheckFailed` with the
check run a second time, which is the guard the test is written to catch.

## Unchanged

`CheckCadence.Periodic`, `CheckInterval`, `RetryInterval`, `InitialDelay`, the machine-free rule,
`MayInstallNow`, the once-per-reason refusal log, and every other outcome `UnattendedTick` reports.
An application that does not set `Cadence` sees no difference.
