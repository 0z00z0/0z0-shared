**Every step of an update is now a window in the studio's own style.** The question with its release
notes, the download with its progress, a refusal with its reason, a failure, and the notice that
nothing newer exists — one window, Mica backdrop, the studio's typeface and colours, light and
dark, and the bracket action button for every choice. The grey Windows task dialog and message
boxes are gone.

**Minor, and a break.** `NativeUpdatePrompts` is removed, `IUpdatePrompts` is awaitable, and the
component's entry point is a new assembly. An application that took the component before this has
three things to change, all of them compile errors. See **What a consumer has to change** below.

## One window, not several

The question, the download that follows it and the answer that follows that are one act. Pressing
"Install now" leaves the window where it is and starts the download in it, so nothing disappears
and reappears in the middle of a gesture. The notice that nothing newer exists and a check that did
not complete open the same window at its last stage.

The window is frameless on a Mica backdrop, always on top, centred on the monitor under the cursor,
and sized to its own content at whatever scaling that monitor has. It shows one stage at a time:

- **The question** — both versions, what installing costs, the release's own notes in a panel that
  scrolls rather than growing, and three choices one per line: install now, not now, open the
  release page.
- **The download** — a bar and a byte count. No way out: closing would take the window off a
  download it cannot stop.
- **The check after the last byte** — verification reports nothing, so a bar sitting full with a
  byte count still under it would read as a download that stalled. The headline and the line move
  instead.
- **A refusal, a failure, a notice** — one sentence and one way out, with the bracket button in the
  brand's attention colours where something went wrong.

Fourteen pictures, light and dark, are in [`zerozero-update.md`](../../zerozero-update.md).

## A new assembly

`ZeroZero.Update.WinUI` holds the window and is the component's entry point. It carries
`ZeroZero.Update.Win32` — the orchestration, the interface and the wording — which in turn carries
`ZeroZero.Update`. All three release as `update-v0.11.0`.

`ZeroZero.Update.Win32` keeps its name and its plain `net10.0` target, and no longer references
`ZeroZero.Win32`: with the task dialog gone there is nothing there to reach for. An application
that wants the flow and a surface of its own still takes it alone.

## The wording is unchanged and now sits apart from the window

`UpdateMessages` carries every sentence the update puts in front of a person, with no window
attached, so a surface written outside this repository words an outcome exactly as the shared one
does. Every sentence is the one 0.10.0 used, word for word: the eleven refusal sentences, the
per-outcome sentences for a check that did not get an answer, and the advice every refusal ends on.

## The path that shows nothing still shows nothing

`UpdateTrigger.Silent` is untouched. It returns before the install path is entered, so nothing
below the prompts can reach a screen: a background check at start-up puts no window in front of
someone who did not ask for one, and an update continuing after the application has exited has
nothing to show anything in. `Scheduled` is unchanged too — nothing but the install question when a
release is found.

Measured rather than reasoned about: a silent run over a service with a release to offer, with the
real window prompts wired up, answered `UpdateAvailable` and created no visible window at any point
in the run.

## A window opened on top of another

A window that dismisses itself when it loses focus — the shared About window is one — would close
the moment the update window appeared in front of it. `ZeroZero.Win32` gains `TransientWindows`, a
count of the application's own short-lived windows: the update window counts itself among them
while it is open, and a self-dismissing window asks `TransientWindows.AnyOpen` before it dismisses.
The About window in `ZeroZero.Brand.WinUI` now asks.

Measured: the About window survived an update window opening on top of it, and closed under a
control window that counts itself among nothing — so the count is what does the work.

**An application whose own window closes on focus loss adds the same question to it.** That is the
one change this release asks for that the compiler will not point at.

## The download's progress

The window draws the bar itself, from the measurements 0.10.0 introduced. `UpdateFlowOptions.Progress`
still works and is now a *second* place for the numbers to go, for an application that also wants
the download on a surface of its own; an application content with the window's bar attaches none.

## What a consumer has to change

1. **Take `ZeroZero.Update.WinUI`** in place of `ZeroZero.Update.Win32`. It carries the old
   assembly, so nothing else moves.
2. **Construct `UpdateWindowPrompts`** in place of `NativeUpdatePrompts`:
   `new UpdateWindowPrompts(new UpdateWindowOptions { ApplicationName = "Product" })`. The owner
   window handle and the topmost flag are gone — the window centres itself and is always on top.
   The theme goes in the options, as it does for a title bar. `ReleaseNotes` replaces the
   `releaseNotes` argument and behaves identically.
3. **An implementation of `IUpdatePrompts` of its own** returns tasks: `AskToInstallAsync`, and
   `Say…Async` for each outcome, plus `BeginDownload` and `Dismiss`. A call must not complete until
   the person has chosen or read what it put on screen.

And one thing the compiler will not catch: **a window of the application's own that closes when it
loses focus** asks `TransientWindows.AnyOpen` before it does.

## What this costs

The component now requires an application able to show a WinUI window. There is no path that falls
back to a message box: an application with no window at all takes `ZeroZero.Update` and supplies
prompts of its own. Both consuming applications confirmed they can show one before this was built.

The common-controls-6 manifest declaration the task dialog needed is no longer needed by this
component. The build kit's WinUI application block still writes it, and other things in an
application may want it.

## Verifying it

Proved by running, not by tests of its own — the owner's standing choice for this component. The
window has no tests. What was looked at: every stage in both themes, captured from the running
window by `scripts/Capture 'Update window' screenshots.ps1`; the silent run creating no window; the
About window surviving one opened on top of it, with a control that says the measurement can fail;
and the window sizing itself to its content at 175 per cent.

**100 per cent scaling has not been seen.** The machine the pictures were taken on has one display
and it runs at 175 per cent, which is the harder of the two: the scale multiplies the content
width and the frame the window reads from itself.

The existing tests that cover what changed still hold. `UpdateFlowTests` runs unchanged apart from
two added assertions that the window is handed the download and taken off the screen before the
application exits; the wording tests moved from `NativeUpdatePromptsTests` to
`UpdateMessagesTests`, keeping every assertion that was not about a task dialog's button ids.

## Unchanged

The published-hash rule, both verification steps, the launch policy, the stale-download sweep, the
scheduler, every outcome a check can report, every trigger, the download's pacing and its final
report, and every sentence a person reads.
