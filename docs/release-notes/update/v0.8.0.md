**A check that fails now says which failure it was.** Two outcomes are added, `TimedOut` and
`RequestFailed`, so the two distinctions a consumer had to recover from an exception type and from
the wording of a sentence are carried by the result itself.

**Minor.** `UpdateCheckOutcome` and `ReleaseLookupOutcome` gain two members each. Nothing is
removed or renamed and no member changes signature, so a consumer that changes no code still
compiles; but a `switch` covering the old set now reaches its default for two situations it used to
name, and that is a consumer-visible change.

## What a consumer on 0.7.1 gets

`Unreachable` covered two situations every other network tool tells apart: nothing at that address,
and something at that address that never answered. `InvalidResponse` covered two more: the
service answering with a failure status, and the service answering with a body that is not a
release.

Neither pair could be separated from the outcome, so an application that wanted four sentences had
to read around it — the type of the exception on `Error` for the first pair, the shape of `Detail`
for the second. Both are fragile. The exception type is an implementation detail of how the request is
made, and `Detail` is a sentence written for a person, so rewording it turns two of an
application's messages into one with nothing failing anywhere.

## What it does now

| Outcome | The situation |
|---|---|
| `Unreachable` | Nothing answered — the name did not resolve, the connection was refused, there is no route, or the answer stopped mid-way. |
| `TimedOut` | Something is at that address and did not answer within `UpdateOptions.RequestTimeout`. |
| `RequestFailed` | The service answered with a failure status rather than a release. The rate limit stays `RateLimited` and never becomes this. |
| `InvalidResponse` | The service answered, and the answer is not a release this version understands: not JSON, not a release object, no tag, or a tag that is not a version. |

`UpdateAvailable`, `UpToDate`, `NoReleases` and `RateLimited` are unchanged, and the new members are
appended rather than filed beside the outcomes they split from, so every existing member keeps the
number it had.

**A cancellation the caller asked for is not a timeout and never was.** It leaves the check as an
`OperationCanceledException`, so it reaches no outcome at all, and the two cannot be confused.

Each new outcome carries a `Detail` sentence saying what happened, and `NativeUpdatePrompts` gives
each one a message of its own: a service that did not answer in time, and a service that answered
with an error.

## What a consumer has to change

An application whose `switch` over `UpdateCheckOutcome` has an arm per outcome gains two arms. One
with a catch-all arm needs nothing to keep working, and gains the two distinctions the moment it
names them.

An application that reads `Error`'s type or `Detail`'s wording to tell a timeout from an unreachable
host, or a failure status from an unreadable release, deletes that code and switches on the outcome.

## Verifying it

Each new outcome has a test that drives the real path to produce it against the loopback release
server: a listener that never answers for `TimedOut`, a closed port for `Unreachable`, a failure
status for `RequestFailed`, and a success status carrying a tag that is not a version for
`InvalidResponse`. A further test requires the caller's own cancellation to throw rather than report
a timeout, and one requires the five messages for a check that failed to be five different
sentences.

## Unchanged

The download, the published-hash rule, both verification steps, the launch policy, the stale-download
sweep and the scheduler. The flow still reports every outcome on a manual run and keeps a failed
scheduled check to the log.
