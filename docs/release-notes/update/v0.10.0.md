**A download can now be put on screen.** The progress a host is handed is paced for a user
interface rather than emitted per network read, a download that completes always ends with a report
carrying its true byte count, and the guide finally documents the path — which is the part that was
actually missing, since an application reading the guide had no way to learn the reporting existed.

**Released** 2026-09-20

**Minor.** No signature changes and no member is removed: `DownloadAsync` gains a default on its
existing `progress` argument, so every call that compiled on 0.9.0 still compiles. The minor number
carries a change in behaviour instead — reports arrive far less often than they did — which an
application that had found the path and wired it up would see.

## How often a report arrives

At most one every 250 ms while bytes are arriving, counted from the last report sent.
`InstallerDownloader.ProgressInterval` is the value.

An interval was chosen over a step counted in bytes because it bounds what a surface is asked to
redraw whatever the file's size and whatever the line's speed. The same byte step is a flood on a
fast connection and a minute of silence on a slow one; four redraws a second is four redraws a
second either way. Before this, one report left the downloader per 64 KiB read — roughly a thousand
of them for a 64 MB installer, each one marshalled to a window.

## The last report is the true one

A download that completes ends with a report carrying its final byte count, whether or not the
interval was due. Without it the interval can leave the last fragment unreported, and a bar that
stops just short of its end reads as a download that stalled.

That report is sent only once the file is whole and its length has been checked against the size
the release declares. **A download that fails, is refused or is cancelled sends nothing after its
last interval report.** That report stands as the last real measurement; nothing follows it
claiming completion, and nothing resets to zero.

## An unknown total stays unknown

`DownloadProgress.TotalBytes` is null where neither the response's `Content-Length` nor the size
the release declares is available, and `Fraction` is null with it. Nothing is invented, so a
surface handed a null total shows a marquee or a plain byte count rather than a percentage that
would be a guess.

## Where a host attaches one

Both layers, unchanged in shape from 0.9.0 and now documented: `UpdateFlowOptions.Progress` for an
application driving the orchestrated flow, and the `progress` argument of
`UpdateService.PrepareAsync` for one driving the service directly. The flow hands the reporter
straight down, so the two report identically. Both install paths carry it — the run that checks and
the install that starts from a release already found.

## The component shows nothing itself

There is no dialog, no bar and no window in this release, for any trigger. The component measures
the download and hands the numbers out; what appears on screen, and whether anything appears at
all, is the application's decision on the application's own surface. The silent trigger is
unaffected in every sense: it downloads nothing, so it reports nothing.

Attaching no reporter remains the whole of turning progress off. An application that supplies none
reads no clock and allocates nothing for progress — the same download, at the same cost, as on
0.9.0.

## What a consumer has to change

Nothing. An application that passes no reporter behaves exactly as it did on 0.9.0.

An application that had already found the path and attached a reporter receives far fewer reports
than before, and one guaranteed last one. A surface that counted reports, or that treated every
report as a repaint it had asked for, is the only kind affected.

One thing worth reading once: verification runs after the last byte arrives and reports nothing, so
a bar that has reached its end sits full while the hash and the signature are checked. The flow's
own result is what finished means.

## Verifying it

Proved by having been run once, against a local server, rather than by tests of its own: the number
of reports arriving for a paced download, their order, the final report's count against the file's
real length on disk, a download with no reporter completing with the same file and no report, a
report reaching a host through the flow rather than through the service, and a download cancelled
part-way sending nothing after its last report.

The two existing tests that already exercised progress still hold unchanged. They assert that
reports are monotonic and that the last one carries the whole length, neither of which the interval
changes.

## Unchanged

The published-hash rule, both verification steps, the launch policy, the stale-download sweep, the
scheduler, the dialogs and their wording, every outcome a check can report, and every trigger.
