**Stopping the update schedule and then disposing on the way out threw from the exit path.** One
guard in `UpdateScheduler.Dispose`; no public member moves.

**Patch.** Nothing is added, removed or renamed, no member changes signature, and a host that
disposes exactly once behaves as it did. A consumer that changes no code recompiles nothing.

## What a consumer on 0.7.0 gets

`Start()` is idempotent and says so, so a host is entitled to read the pair as symmetric and stop
the same way. It was not: `Dispose()` cancelled its cancellation source and then disposed it, and a
second call cancelled the disposed source, which throws `ObjectDisposedException`.

Two calls is the ordinary shape rather than a mistake. A host that stops the schedule when the tray
menu's Exit is chosen, or before an installer it launched takes over, and then disposes the
scheduler with everything else on the way out of `Main`, calls it twice. **The throw lands on the
exit path, after the work it guards is already done**, so what a person sees is an application that
did everything asked of it and then failed as it closed.

## What it does now

The first call cancels and disposes; every later call returns at once and costs nothing. The
schedule is stopped either way, so nothing about the check interval, the run count or the initial
delay changes.

## Verifying it

One test starts a schedule, lets a run happen, disposes twice and requires the second call to
throw nothing. It fails against 0.7.0's code.

## Unchanged

The schedule itself: the initial delay, the interval, one run at a time, the run counter, and a
check that throws being logged while the schedule goes on. `ZeroZero.Update.Win32` carries no
change.
