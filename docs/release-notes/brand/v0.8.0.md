**The About box shows the release notes instead of linking to GitHub, the popup closes as soon as
it loses focus, and the brand typeface loads again under a package reference.** A consuming
application supplies one new address and gets the notes; one that supplies none keeps the row it
had, less the GitHub button.

**Minor.** Two changes reach the screen of every application on this component without it opting
in: a button is gone from the shared row, and the popup now dismisses itself. Nothing is renamed
and nothing has to be recompiled against a changed signature.

## "What's new" replaces the GitHub button

The row of three is now **What's new / Website / Donate**. Pressing "What's new" fetches the notes
and shows them in a panel inside the About surface — no browser, no second window. Pressing it
again closes the panel.

**Where the notes come from is per-application data**, supplied the same way the repository address
always was: a new `ReleaseNotesUrl` on `AboutInfo`. It is optional, and an application that leaves
it unset gets no "What's new" button at all, the same rule the update button already follows.
`RepoUrl` stays exactly where it was and still feeds the console banner.

```csharp
Info = new AboutInfo
{
    AppName         = "ExampleApp",
    Version         = "1.2.3",
    Description     = "What the app does.",
    RepoUrl         = "https://github.com/0z00z0/ExampleApp",
    ReleaseNotesUrl = "https://github.com/0z00z0/ExampleApp/releases/latest/download/whats-new.txt",
};
```

The notes are plain text. Roughly the first four thousand characters are read and the panel scrolls
inside a fixed height, so a page of any length leaves the window a small window.

**The fetch fails fast and says so in one sentence.** Three seconds, one attempt, no retry: while
it runs the panel reads "Fetching the notes…", and a fetch that does not answer leaves "The release
notes could not be fetched." and nothing else. Nothing blocks while it waits — the button returns
at once and the rest of the window stays live — and nothing is fetched at all until the button is
pressed. Measured against an address that refuses the connection: the panel opens 87 ms after the
press and the failure sentence replaces the waiting line 2.3 seconds later.

Closing the window abandons a fetch in flight, and a reply that arrives afterwards touches nothing.
A control hosted in a page does the same when it is unloaded.

## The popup dismisses itself

`BrandAboutWindow` closes the moment it loses focus. **One rule, with no exception for what is on
screen** — the notes panel being open does not hold the window open. Escape does the same thing,
and so does the close button; all three take one path, which stops the fetch before the window
goes.

Two guards make that rule safe to state so plainly:

- **A deactivation arriving before the window has ever been activated is ignored.** The window is
  still taking focus at that point, and treating it as a dismissal made a fast double-click on
  whatever opens the window open it and close it again in the one gesture. The latch is
  load-bearing where it applies — defeating it closes the window on that gesture every time — but it
  does not cover every ordering. A second click that lands after the window has taken focus is an
  ordinary click away from it, and the one rule closes the window. Driven across gaps from 10 ms to
  400 ms, the outcome tracks which event arrives first rather than the gap itself, so a double-click
  that happens to close the popup is the rule working, not a defect.
- **A dismissal already under way cannot start a second one.** Closing deactivates the window, and
  that deactivation arrives straight back at the same handler.

**What this means for a consuming application.** An About popup that used to stay open while the
reader looked at something else now closes. Nothing has to be wired up for it, and there is no
setting: an application that needs an About surface which stays put hosts `BrandAboutControl` in
its own page instead, which is unaffected.

## The window's height comes from its own layout

The popup sized itself from a measure taken before its content was arranged, and fell back on a
fixed 270 units when that measure came back empty. It now runs the layout first and reads the
height off it, rounding up rather than to nearest, so the client area is never a pixel short of the
last row. The constant is gone.

It also **never exceeds the monitor's work area**. Nothing in this window scrolls, so a window
taller than the screen loses its last rows with no way to reach them; an over-tall window is now
capped at the work area and sits against its top edge, where the rows that survive are the ones
read first.

With ordinary content nothing here is visible: measured on a 3840×2400 display at 175 %, the
client area is 338 units tall with the libraries list closed, 427 with it open and 379 with the
notes shown, and every row — the libraries toggle included — falls inside it in each of those
states and in the opening frame.

## The brand typeface loads under a package reference

`BrandAboutControl`, `BrandAboutWindow` and `BrandResources.xaml` each named the face at
`ms-appx:///Assets/Fonts/CascadiaMono.ttf` — the root of the consuming application's own output,
with no assembly in the path. Where the font lands depends on the route:

| Route | `Assets\Fonts\` at the output root | `ZeroZero.Brand.WinUI\Assets\Fonts\` |
|---|---|---|
| Project reference | Yes | Yes |
| Package reference | **No** | Yes |

A package reference puts the library's content beside the assembly and nothing at the root, so the
URI resolved to no file at all. All three now ask at
`ms-appx:///ZeroZero.Brand.WinUI/Assets/Fonts/CascadiaMono.ttf`, which exists on both routes.

**Nothing reported it.** A font URI that resolves to no file raises no warning, no error and no log
line: the face falls back to the family name, and the family name is `Cascadia Mono`. On any machine
with Cascadia Mono installed — which includes every machine with a recent Windows Terminal — the
fallback is the same face, so the About box looked exactly right while loading nothing. What an
application actually got was the installed system copy where there was one, and the default UI face
where there was not.

**The About box looks the same after upgrading on a machine that has Cascadia Mono installed**,
because that machine was already rendering the same face by fallback. On a machine without it, the
About box changes from the default UI face to the brand face — which is the point of shipping the
font.

### Proving it, given that looking at it proves nothing

A screenshot cannot tell the working case from the broken one, and neither can a text measurement:
with the same face installed system-wide, a font file that does not exist at all renders at exactly
the same width as one that does.

An image source does report whether it loaded, so the same resource machinery is pointed at the same
URI. `SvgImageSource` answers on a three-way scale — a file found and decoded, a file found that is
not an SVG, and nothing at that path — so pointing it at the `.ttf` separates a path that resolves
from one that silently does not.

Two applications built from one source set, differing only in the reference:

| URI | Package route | Project route |
|---|---|---|
| `…/ZeroZero.Brand.WinUI/Assets/Fonts/CascadiaMono.ttf` | found | found |
| `…/Assets/Fonts/CascadiaMono.ttf` — 0.7.0's path | **not found** | found |
| A font path deliberately naming nothing | not found | not found |
| An image the application really has | found and decoded | found and decoded |

The old path gets the same answer on the package route as the deliberate control that names nothing,
and a different answer from the same file asked for at the new path in the same run. The URIs fed to
the instrument are read back off the live `BrandAboutControl` and the merged `BrandFontFamily`, so
what is measured is the string the library asks with.

`BitmapImage` was asked the same nine questions and cannot answer them: it reports a network error
for a file that is there as well as for one that is not.

### The test that would have caught it

`BrandFontPathTests` packs the component for real and holds every font URI in the markup to the
entries the package carries, in both directions: a URI naming a file the package does not carry
fails, and a font shipping at a path no markup asks for fails too. A test asserting only that the
file exists in the repository would have passed throughout.

Both directions are mutation-tested. Reverting the markup to 0.7.0's URI with the package untouched
reddens it, naming the missing entry; moving the packed path off the assembly folder with the markup
untouched reddens both directions.

### The correction to 0.7.0's notes

0.7.0 said the font is addressed through the consuming application's output root, "which is where
the packed font lands". That is true of a project reference and false of a package reference.
Released notes are not rewritten; this page is the correction, and
[`zerozero-brand.md`](../../zerozero-brand.md) carries the per-route table.

## Unchanged

`BrandAboutControl.SetInfo` and `ContentResized`, `BrandAboutOptions` with its two callbacks,
`ExternalLibrary`, `ConsoleBanner`, `Brand`, the nine colour keys with their brushes, and the theme
behaviour. `ZeroZero.Brand.Core` gains one optional member on `AboutInfo` and nothing else, and
releases under the same number.
