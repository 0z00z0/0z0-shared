**The module is published as six NuGet packages**, both WinUI assemblies included. A consumer can
now pin a version instead of a sibling checkout, which is the first arrangement in which a pin
governs a local build as well as CI. **The feed authenticates every read**, so adopting the package
route costs a token that the sibling route never needed — the detail is below, and it is the one
thing to know before trying it.

**Minor rather than patch.** A new way to consume the module is a capability, not a fix. **No
public API changes**, no behaviour changes, and nothing is removed: an application recompiles
unchanged, and a `ProjectReference` on a sibling checkout keeps working exactly as it did.

The package version is the tag without its `v`, so one number pins either route. Taking
`ZeroZero.Mqtt.WinUI` brings the whole module and both brand assemblies with it, as the single
project reference always did.

**The two WinUI packages carry their compiled XAML and their `.pri`** beside the assembly, and the
consuming build merges that resource index into its own. A consumer holding nothing but the two
`PackageReference`s — no project reference, no checkout of this repository anywhere — builds, runs
and renders both `BrandAboutControl` and `MqttSettingsPanel`, brand typeface included.

## The feed authenticates every read

Packages go to `https://nuget.pkg.github.com/0z00z0/index.json` and nowhere else. **GitHub
authenticates every read even for a public package** — an anonymous request returns `401`.

So the package route needs a token carrying `read:packages` wherever a restore happens: on a
developer's machine, and on a CI runner. A consumer's own workflow gains a secret it did not have,
where today it clones a public repository with no credential at all. **That is the whole cost of
the route, and it is worth knowing before the first red build rather than after it.**

A consuming repository also needs a `nuget.config` naming the feed **and** mapping which source may
answer for which name, so that nothing on nuget.org can resolve a `ZeroZero.*` package; none of the
six names is reserved there. Both files are in
[the README](https://github.com/0z00z0/0z0-shared#the-package-route).

## What the pin actually buys

A sibling pin governs CI and nothing else. The `ProjectReference` resolves through
`ZeroZeroSharedDir`, and nothing reads the pinned-ref file to decide which sources compile, so every
local build, local test run and locally built installer silently carries whatever the sibling
working tree currently holds.

**A package version resolves the same source everywhere**, because a restore never consults a
working tree. That is the substantive difference between the two routes, and the reason this release
exists.

## Publishing is part of the release job

`.github/workflows/release.yml` packs the solution and pushes to the feed before it creates the
release, so a published release means the packages are actually live rather than merely announced.

The push authenticates with the per-run `GITHUB_TOKEN` — minted for the run, so there is no secret
to create, rotate or forget. `--no-symbols`, because GitHub Packages has no symbol server and the
`.snupkg` would only fail the step. No `--skip-duplicate`, because the `409` that means *this
version is already published* is exactly the failure a release job exists to catch.

## The defect that made this possible

`ZeroZero.Brand.WinUI` ships the Cascadia Mono brand typeface and its OFL licence as `Content`.
Those two files packed to NuGet's default `content\` and `contentFiles\`, while a consuming WinUI
build resolves a referenced library's assets from `lib\<tfm>\<assembly>\Assets\` — so the consumer
copied from a path the package did not carry and its build failed with two `MSB3030` errors. Naming
the destination is the whole of the fix.

[Issue #14](https://github.com/0z00z0/0z0-shared/issues/14) held that neither WinUI assembly could
be packed at all, because `dotnet pack` dropped the compiled XAML and the resource index. **That is
not true at Windows App SDK 2.2.0** — it is measured false, and the issue records what was actually
wrong.

## Also in this tag

- **A package readme.** `PACKAGE.md` is packed into all six packages and is what the feed shows.
  It was the only outstanding pack warning.
- **No duplicate font items.** An implicit glob already took everything under `Assets\` as
  `Content`, so each font was two items packing to two destinations. One item each now.

## Deliberately not in this tag

- **Neither consumer is changed.** ChargeKeeper and HyperVManagerTray keep their sibling
  `ProjectReference`s, and adopting the packages is each application's own decision. The two routes
  stand side by side; the package route is an addition, not a replacement.
- **The panel's string override still loses to the library's own.** A consumer supplying its own
  `.resw` for a panel key does not win, under either route — the library's value does. It is a
  loader defect in `MqttResourceStrings`, not a packaging one, and it is
  [tracked separately](https://github.com/0z00z0/0z0-shared/issues/16).
- **Three things about the packages are unverified**, listed on issue #14: an MSIX-packaged
  consumer, a build on a CI runner, and a runtime identifier other than `win-x64`. The round trip
  through the live feed *is* verified — the six packages were pushed by this release job, restored
  from the feed with a `read:packages` token, built and rendered.
