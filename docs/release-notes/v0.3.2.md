A defect release. **No API change** — no public signature is added, removed or altered. What it
carries is a connection defect that abuses a broker, two eviction paths that lost work rather than
retrying it, and a backoff floor that was never waited.

## The connect storm — raise a pin for this one

**Every released version before this one hammers the broker whenever the connect sequence throws.**
Measured against the fake broker on a loopback listener: **361 CONNECTs in three seconds**, where the
backoff intends at most one. A real broker answers that with rate-limiting or a ban, and the client
has no idea it is doing it.

The path is short. The maintain loop drops its own socket when the connect sequence throws — a
listener that fails, the subscription, an eviction — so the next pass retries instead of leaving a
half-built session standing. MQTTnet raises that self-inflicted drop as an ordinary disconnect with
the "was connected" flag set, which is exactly what a peer going away looks like, so the wake guard
passes and the loop wakes itself. The wake cancels the wait the round has just earned. The escalation
still runs and still doubles; nothing ever waits it out. The backoff is not weakened on this path, it
is absent.

It needs a throwing connect sequence to appear, which is why no amount of ordinary running finds it:
in development the connect sequence does not throw.

**The fix is in the loop, not in the escalation.** A dropped link now arms a signal of its own, and
only the long poll of a session that was up may be cut short by it. A backoff wait is left to run —
the loop already knows the link is down, so a drop tells it nothing it can act on sooner. A genuine
peer disconnect still wakes the loop promptly, because that is what the long poll is waiting in.

### Which versions carry it

| Version | Connect storm |
|---|---|
| `v0.1.0`, `v0.2.0`, `v0.2.1`, `v0.3.0`, `v0.3.1` | **Present** |
| `v0.3.2` | Fixed |

**A tag number is not evidence that a defect is gone.** `v0.3.1` was cut over this exact loop while
adding seventeen assertions around the backoff it defeats. Every one of them passed, because they
assert the escalation and the escalation was never wrong — the thing that cancels it went untouched.
Coverage of a mechanism is not coverage of the code that renders the mechanism moot.

## Two eviction paths lost work rather than retrying it

The rule already in force is that a publish which did not land is never recorded as sent. Two
eviction paths broke it.

- **A superseded device id.** `ClearRetiredIdentityAsync` took the retirement out of its slot with an
  interlocked exchange and then discarded the publish's answer. A refused or half-sent eviction was
  gone for good: the old device stayed on the receiver with every retained value intact, and nothing
  in the process still knew it existed. The retirement is now put back — into an empty slot only, so
  a retirement recorded while this one was in flight supersedes it — and the next connect tries
  again.
- **A cancelled eviction batch.** `FlushEvictionsAsync` rolled back a *refused* batch but not a
  cancelled one: the in-flight limiter's wait sits outside the per-message try, so cancellation threw
  straight past the rollback with the pending set already emptied. The keys were then lost from every
  place that knew them, and the values stayed retained for ever under entities the document no longer
  declares. A cancelled batch now rolls back exactly as a refused one does.

## The first retry is three seconds, not six

The doubling was applied before the wait rather than after it, so a broker that was simply down saw
**6, 12, 24, 48, 60, 60** and the three-second floor was a value nothing ever waited. It is now
**3, 6, 12, 24, 48, 60, 60**, which is what the floor's name, and every description of the mechanism,
already said. A transient drop retries at three seconds; only a repeat costs more. The cap, the flap
window and the stability reset are unchanged.

## Four smaller corrections

- **`PublishNowAsync` reported failure when there was nothing to publish.** A connection with no
  channels — a device that declares only commands, or one whose groups are all switched off — sent
  nothing and returned false, which a settings panel shows the user as a refused publish. Nothing to
  publish is not a failed publish.
- **The self-cleared-echo discriminator is asserted at last.** A command topic this connection
  empties comes straight back: it is subscribed to its own command subtree, and the broker delivers
  the clear with the retain flag down and a zero-length payload, which on the wire is exactly what
  somebody sending an empty command looks like. For a text entity an empty string is a value, so a
  broken discriminator turns "clear a stuck command" into "set the entity to empty" on this connect
  and on every reconnect after it. Both directions are now pinned, including that the note is spent
  on one message rather than swallowing every genuine empty command afterwards.
- **A throwing command handler cannot end the work queue.** The queue has one reader so that a
  command's read-modify-write finishes before the next starts, which makes it a single point of
  failure: an uncaught throw would end the reader and leave every later command enqueued into a queue
  nothing drains, with no error after the first. It was already guarded; it was not asserted.
- **An unchanged endpoint is not handed over again.** A consumer persists what the endpoint callback
  hands it, so a consumer that re-applies on a settings change would reconnect on the strength of its
  own success — a self-sustaining loop with no local symptom, every part of it working as designed.
  Also already guarded, also unasserted.

## Verified

699 unit tests across `ZeroZero.Brand.Core`, `ZeroZero.Config`, `ZeroZero.Mqtt` and
`ZeroZero.Mqtt.Discovery`, all passing on `windows-latest` in Release. The release is gated on them.

Nine tests are new, and every one was confirmed to fail against the code it guards before the fix
went in — the connect-storm test against `v0.3.1`'s source exactly as it shipped, which is where the
361 was measured. That test counts CONNECTs at the broker over a wall-clock window rather than
sampling a flag: the connection state oscillates far faster than anything can read it, which is how
the defect stayed invisible, and a slow machine can only lower a count.

## Pre-1.0 — what this patch means for a pin

While the major version stays `0`, a **minor** bump may break the API and a **patch** never does.
This one adds no public member and removes none, so raising a pin from any `v0.3.x` to `v0.3.2`
cannot change what an application compiles. It changes three things an application can observe: the
broker is no longer hammered on a throwing connect, the first retry after a drop is three seconds
rather than six, and `PublishNowAsync` answers true where a connection has no channels to publish.

**Raising the pin is not by itself enough for a consumer that builds locally.** The project reference
resolves through `ZeroZeroSharedDir`, which defaults to the sibling working tree; nothing reads the
pinned-ref file to decide which sources compile. A local build, a local test run and an installer
built on a developer's machine carry whatever that tree holds. Check the sibling clone out at
`v0.3.2` — the pin file records the intent, the working tree decides the build. The MQTT guide's
[Take the reference](../zerozero-mqtt.md#1-take-the-reference) states this in full.

## Everything else

Unchanged from `v0.3.1`: the seven source projects and their one-way dependency, every public
signature, the entity model, the device document, identity, the ledger's shape on disk, the
encryption model, the endpoint sweep and every behaviour of the panel. `v0.3.0`'s notes remain the
account of what that release changed, and `v0.1.0`'s **Differences from an earlier shape** tables
remain the migration reference.

## Requirements

.NET 10 SDK. Windows 10 1809 (build 10.0.17763) or later with the Windows App SDK for the WinUI
assemblies; `ZeroZero.Brand.Core`, `ZeroZero.Config`, `ZeroZero.Mqtt` and `ZeroZero.Mqtt.Discovery`
are plain `net10.0` and portable in isolation. The MQTT module requires an MQTT 5.0 broker and, for
discovery, Home Assistant 2024.11.0 or later.

## How to consume it

There is no NuGet feed: neither `ZeroZero.Brand.WinUI` nor `ZeroZero.Mqtt.WinUI` can be packed, so
this release is the tag and these notes — which is all a `ProjectReference` on a pinned checkout
needs. Pin `v0.3.2` as the `ref` of the consumer's second `actions/checkout`, or as
`--branch v0.3.2` on a sibling clone.
[Pin a tag](https://github.com/0z00z0/0z0-shared/blob/v0.3.2/README.md#3-pin-a-tag) in the README
carries both shapes, the MSBuild property that lets CI redirect the reference, and the item-glob
exclusions a workspace-subfolder checkout needs.
