**A monitor lookup from any point, and two more parts of the task dialog.** Three additions, each
one a consuming application had to keep its own code for.

**Minor.** Public members are added and none change, so nothing a consumer wrote stops compiling.

## The monitor a point falls on

`MonitorMetrics` answered for the cursor's monitor and the primary monitor and nothing else. A
window restoring a position saved in configuration needs neither: it resolves the monitor from the
**centre of the saved rectangle**, then clamps against that screen's work area and scale.

`MonitorMetrics.ForPoint(x, y)` answers that, and answers for the **nearest** monitor when the point
is on no monitor at all — which is the case it exists for, a window remembered on a screen since
unplugged. Without it, that window opens where nobody can reach it, or the lookup stays in the
application.

`ForCursor` is the same lookup at the cursor's position and behaves as it did.

The work area and the scale are the point's own monitor's, in physical pixels, and `ClampInto` on
`NativeRect` does the placement. Which monitor gets which window is still the caller's decision.

**On a single monitor this lookup and the primary-monitor fallback give the same numbers**, so a
swap checked on one screen says nothing about the case the lookup is for.

## The task dialog's stock Cancel button

`TaskDialogRequest.StockCancelButton` adds the system's own Cancel: the system's wording in the
user's display language, in the place a Cancel button belongs. Without it a consumer wanting Cancel
had to spell it as a third custom button, in one language, and hope it landed in the right place.

It reports `TaskDialogButton.CancelId`, the same id the title-bar cross and Escape report, and the
custom buttons in `Buttons` are untouched.

## Sizing the dialog to its content

`TaskDialogRequest.SizeToContent` widens the dialog to fit its longest line instead of wrapping at
the standard width. Measured on the same request with the same text: 659 pixels wide without it,
997 with.

## The dialog still has no fallback

`Show` throws where the dialog cannot appear, and that has not changed. No message box can carry a
row of custom buttons, so any fallback chosen here would silently change which button ids a caller
can get back, and the wording of a simpler prompt is the application's. An application whose menu
item must always lead somewhere branches on `NativeTaskDialog.IsAvailable` and keeps its own prompt.
The consumption checklist now says so.
