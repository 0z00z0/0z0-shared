**A broker whose certificate cannot be made to verify can now be connected to, and the settings
panel is where certificate trust is chosen.** A fourth trust mode accepts whatever certificate the
far end presents, and the panel carries a Certificate trust row offering all four.

**Released** 2026-09-28

**Minor, and nothing breaks.** The three existing modes behave exactly as they do on 0.7.3: the
platform's own trust is still the default, a pinned mode still refuses a certificate that is not the
pinned one, and an unusable pin still refuses rather than falling back. An application that sets
`MqttSettings.CertificateTrust` itself needs no change, and one hosting the settings panel gets the
new row without wiring anything.

## The fourth mode

`MqttCertificateTrustMode.AcceptAny`, reached as `MqttCertificateTrust.AcceptAny`, accepts every
certificate. The traffic stays encrypted and nothing checks that the broker is the machine it claims
to be, so anything that answered in its place is accepted too. It is the last resort for a broker
whose certificate cannot be made to verify — the setting other MQTT tools offer as ignoring
certificate validation.

Like the platform's own trust, it needs no value alongside it: `Validate()` returns null for it as
it stands, where the two pinned modes still refuse without a thumbprint or a certificate.

The member is appended to the enum, so every existing member keeps its number, and the setting
serialises by name.

## The panel

`MqttSettingsPanel` carries a **Certificate trust** row under **Encrypted connection**. The dropdown
lists the certificates this machine trusts, one certificate by thumbprint, one certificate pasted in
full, and any certificate the broker presents. A box for the thumbprint or the base64 certificate
appears under the dropdown for the two modes that name one, and the line below it carries either
that box's fault or, for the last entry, the one sentence saying what it gives up.

- **Apply and Test are gated on the same one answer as before.** A mode that names a certificate
  with nothing in the box disables both, so an incomplete pin can neither be saved nor tested, and
  is never quietly saved as the platform's own trust.
- **Test uses the trust in the field**, not the saved one, like every other value on the row.
- **A box not yet typed into carries no message**, exactly as the typed port does.

Thirteen string keys are added — the four mode names, the row's label, description, info text and
screen-reader subject, two placeholders and three messages. A host translating the panel takes them
from `MqttStrings.Builtin` as usual; anything it does not answer falls back to the module's en-GB.

## Applying it from code

`MqttBrokerEdits` stages the mode and its one value as `TrustMode` and `TrustValue`, reads back as
`Trust`, and commits it with the rest of the broker block on Apply. `ValidatePort` and
`ValidateTrust` answer per field for the message beside each box; `Validate` is still the single gate
both buttons read.

## Unchanged

Every other public member, the endpoint search, the reconnect ladder, what reaches the log, and
`ZeroZero.Mqtt.Discovery`.
