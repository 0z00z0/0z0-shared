**A broker that cannot be reached no longer fills the host's log.** A value sent while there is no
link is skipped without a log line, an outage is one line when the link goes and one when it
returns, and no connection or send failure hands an exception to the log sink. Issue #33.

**Patch.** Nothing is added, removed or renamed, no member changes signature, and the reconnect
cadence and the resend on connect are unchanged. A consumer that changes no code recompiles nothing.
What changes is what reaches `ILogSink`, and that `PublishAsync` answers false without a line while
there is no link.

## What a consumer on 0.7.2 gets

Two things, both only while the broker is unreachable:

- **A stack trace per value.** `Publish(key, payload)` already returned in silence without a link,
  but a value signalled with `RequestPublish` was still sent, failed with the client library's
  not-connected exception, and reached the log sink as an Error carrying that exception — which a
  host prints with its stack. One per value, for as long as the outage lasts.
- **An Error per reconnect round**, every 3 to 60 seconds, reading "no endpoint connected", and no
  line at all at the moment the connection was lost.

## What it does now

- **A value sent without a link is skipped.** Both send paths, and `PublishAsync`, return without
  sending and without a log line. Every connect already resends every channel's current value, so
  the latest value per channel arrives when the link returns.
- **One line out, one line in.** A lost connection, or a first connect that finds the broker
  unreachable, writes one Info line with the reason, saying that sending resumes when the
  connection returns. Retries during the outage write nothing. The Info line on reconnect is
  unchanged. A session the connection ends itself — an apply with changed parameters, a resume from
  standby — writes no loss line.
- **A refusal is still an Error, written once.** A broker that refuses the login or the connection,
  or a certificate the connection does not trust, is logged as one Error line when first seen and
  not again until the reason changes or a connect succeeds. It is told apart from an unreachable
  broker by the CONNACK reason code and by whether a certificate was presented, as the endpoint
  sweep already classifies every attempt.
- **One line, no exception.** Connection and send failures are logged as a single line with the
  reason in words, and no exception reaches the sink. A send that fails because the link dropped
  under it counts as the loss.

A host that sends only while `IsConnected` is true, to keep 0.7.2's log quiet, stays correct and
can keep doing so.

## Verifying it

No test is added. The behaviour is proved by one measurement against the repository's test broker,
fronted by a relay that is stopped mid-run and started again while values are sent every 50 ms
through `RequestPublish`, `Publish` and `PublishAsync`:

| Case | 0.7.2 | 0.7.3 |
|---|---|---|
| Link lost for 53 s, four reconnect rounds, about 2 600 sends | 1 017 Error lines, 1 013 carrying an exception | One Info line at the loss, one on return, no Error |
| First connect with the broker unreachable, three rounds | 62 Error lines, 59 carrying an exception | One Info line |
| Login refused for three rounds, then a different refusal, then accepted | One Error per round | One Error, one more when the reason changed, Info on connect |
| Certificate not trusted, three rounds | One Error per round | One Error |

In both versions the connect after the outage resends the last value set during it, and a channel
that was never signalled.

## Unchanged

The reconnect ladder and the flap rule, the resend of every channel on connect, the connection
states a panel reads, and every public member. `ZeroZero.Mqtt.Discovery` and `ZeroZero.Mqtt.WinUI`
carry no other change.
