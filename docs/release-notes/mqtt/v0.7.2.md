**A settings change applied after teardown, and a reconnect still in flight while the process exits,
could each end the process.** Two gates, one in the connection and one in the discovery publisher;
no public member moves.

**Patch.** Nothing is added, removed or renamed, no member changes signature, and a connection that
is never torn down behaves exactly as it did. A consumer that changes no code recompiles nothing.

## What a consumer on 0.7.1 gets

`MqttConnection.ApplyAsync` is what a host calls on every settings change, and `Dispose` is what it
calls on the way out. The two are not ordered by anything: a settings panel that applies while the
application is closing, a watcher that fires on the configuration file as the process exits, or a
broker reconnect already under way when the tray's Exit is pressed all put one after the other.

On 0.7.1 the reconcile gate was disposed by the teardown and the reconcile had no disposal check, so
each order had its own failure:

- **An apply that starts after the teardown** waits on a disposed gate and throws
  `ObjectDisposedException` out of the wait — inside the host's settings-changed handler, where a
  settings dialogue is the only thing on screen.
- **An apply already inside the gate when the teardown lands** passes the wait, does its work, and
  then throws out of its own release in the `finally`. Nothing is above it to catch that: the throw
  leaves an async continuation on a thread-pool thread, and an unobserved exception there is a
  process that stops.

`DiscoveryPublisher` carried the same shape on its announcement gate, reached the other way round:
the connection holds the publisher as its listener, so a reconnect landing during exit announces
into a publisher that has already been disposed.

The one-line summary is that both gates were guarded on the wait side and not on the release side,
so **an ordinary settings change or an ordinary exit could take the process down**, at a rate set by
how often the two collide rather than by anything a consumer does wrong.

## What it does now

Both gates answer the same way. A torn-down connection reconciles to nothing: `ApplyAsync` returns
without touching the gate, so no maintain loop is started against a client that is already disposed.
A torn-down publisher announces nothing: the announcement pass and the retained-document sweep both
return before the gate.

Neither gate is disposed any more. Nothing takes their wait handles, so they hold nothing to
release, and leaving them alone is what gives a pass that is already past the check something to
release into. Disposal is idempotent on both types, so a host that tears down explicitly and then
disposes on the way out pays nothing for the second call.

## Verifying it

Six tests, three per type. Four of them fail against 0.7.1's code — the late apply and the late
connect, and the teardown driven from inside the gate through a hook the gate calls. The remaining
two pin that a second disposal stays free; they pass either way, because what 0.7.1 did twice was
already harmless, and they exist so that a later guard cannot make it costly.

## Unchanged

Everything a live connection does. The reconcile itself, the maintain loop, the retained-document
eviction, the ledger and the entity projection. `ZeroZero.Mqtt.WinUI` carries no other change.
